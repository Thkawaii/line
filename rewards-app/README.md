# ระบบสะสมคะแนนพนักงาน (Community Web Application)

เว็บแอปสะสมคะแนนและแลกของรางวัลสำหรับพนักงาน พัฒนาตามไฟล์ออกแบบ Figma ที่ส่งมา
แบ่งเป็นสองฝั่งในโปรเจคเดียว

- **ฝั่งพนักงาน** ออกแบบมาเพื่อมือถือ จำกัดความกว้าง 480px และจัดกลางเมื่อเปิดบนจอใหญ่
- **ฝั่งผู้ดูแลระบบ** แดชบอร์ดเต็มจอ มีเมนูข้างแบบย่อได้ และย่อลงเป็นแถบนำทางล่างบนจอเล็ก

| ส่วน | เทคโนโลยี |
| --- | --- |
| หน้าบ้าน | React 18 + Vite 5 + Tailwind CSS 3 + React Router 6 |
| หลังบ้าน | Go 1.22 + net/http + PostgreSQL (ไดรเวอร์ `lib/pq`) |
| ยืนยันตัวตน | JWT (HS256) อายุ 7 วัน รหัสผ่านแฮชด้วย PBKDF2-HMAC-SHA256 |

## เริ่มใช้งาน

ต้องมี Go 1.22 ขึ้นไป (สำหรับ backend), Node.js 18 ขึ้นไป (สำหรับหน้าเว็บ) และ PostgreSQL 14 ขึ้นไป

### 1. ฐานข้อมูล

ระบบใช้ฐานข้อมูลชื่อ **line** และจะสร้างให้อัตโนมัติตอนสั่ง `go run ./cmd/migrate`
ขอแค่มี PostgreSQL เปิดอยู่และบัญชีที่ใช้มีสิทธิ์สร้างฐานข้อมูล

**ถ้ามี Docker** สั่งทีเดียวจบ ค่าตรงกับ `.env.example` อยู่แล้ว

```bash
docker compose up -d
```

**ถ้าติดตั้ง PostgreSQL ไว้ในเครื่องเอง** ไม่ต้องสร้างฐานข้อมูลเอง แค่เปิด service
ให้ทำงานอยู่ แล้วแก้รหัสผ่านใน `backend/.env` ให้ตรงกับของเครื่องคุณ

```
DATABASE_URL=postgres://postgres:รหัสผ่านของคุณ@localhost:5432/line
```

ตรวจว่าต่อติดไหมด้วย `go run ./cmd/check` ในโฟลเดอร์ `backend` — ถ้าต่อไม่ได้
มันจะบอกสาเหตุและวิธีแก้ให้เลย

### 2. หลังบ้าน

```bash
cd backend
cp .env.example .env          # แก้ DATABASE_URL ให้ตรงกับรหัสผ่าน PostgreSQL ของคุณ
go run .                      # http://localhost:4007
```

**แค่นี้พอ** ตอนเปิดเซิร์ฟเวอร์ระบบจะเตรียมฐานข้อมูลให้เอง

1. ยังไม่มีฐานข้อมูล `line` → สร้างให้
2. ยังไม่มีตาราง → สร้างตารางและบัญชีตั้งต้นให้
3. มีตารางอยู่แล้ว → ไม่แตะอะไรเลย ข้อมูลที่ใช้งานอยู่ปลอดภัย

คำสั่งเสริมที่ปกติไม่ต้องใช้

```bash
go run ./cmd/check            # ตรวจการเชื่อมต่อฐานข้อมูล ใช้ตอนเจอปัญหา
go run ./cmd/demo             # ใส่ข้อมูลทดสอบพร้อมรูป ครบทุกรูปแบบ
go run ./cmd/demo clear       # ลบข้อมูลทดสอบทิ้ง
go run ./cmd/seed             # สร้างบัญชีตั้งต้นคืน เผื่อเผลอลบทิ้ง
go run ./cmd/migrate          # ล้างทุกตารางแล้วสร้างใหม่ — ข้อมูลเดิมหายหมด
```

### ข้อมูลทดสอบ

`go run ./cmd/demo` ใส่ของรางวัล กิจกรรม แบนเนอร์ และคำถามพร้อมรูปภาพให้ทันที
รูปอยู่ที่ `backend/db/demo/` และจะถูกคัดลอกเข้าโฟลเดอร์ `uploads` ให้เอง

ของรางวัลครอบคลุมทุกเคสที่หน้าเว็บต้องรับมือ — มีส่วนลด, ของหมด, เฉพาะ Silver,
เฉพาะ Elite, กิจกรรมพิเศษเหลือ 5 วัน, วันสุดท้าย, ยังไม่ถึงวันเริ่ม, หมดเขตแล้ว,
ซ่อนไว้ และของที่ยังไม่ใส่รูป ส่วนกิจกรรมมีทั้งแบบลงทะเบียน แบบโหวต แบบไม่จำกัดจำนวน
แบบไม่มีรูป และแบบปิดรับแล้ว กิจกรรมตั้งวันเริ่มและวันสิ้นสุดได้ สำหรับงานที่จัดหลายวัน

พนักงาน `1875` จะได้ 3,200 คะแนนและเลื่อนเป็นระดับ Silver เพื่อให้เห็นทั้งของที่แลกได้
และของที่ระดับยังไม่ถึง

บน Windows PowerShell ใช้คำสั่งเดียวกันได้ทั้งหมด

### 3. หน้าบ้าน

```bash
cd frontend
npm install
npm run dev                   # http://localhost:4008
```

ตอน dev คำขอที่ขึ้นต้นด้วย `/api` จะถูก proxy ไปพอร์ต 4007 ให้อัตโนมัติ ไม่ต้องตั้ง CORS เพิ่ม

### เปิดจากมือถือหรือเครื่องอื่นในวงแลน

vite ผูกกับ `0.0.0.0` อยู่แล้ว เครื่องอื่นเปิด `http://<IP เครื่องคุณ>:4008` ได้ทันที
ใช้ได้ครบทุกหน้าทั้งฝั่งพนักงานและผู้ดูแล **ไม่ต้องตั้ง https**

ทั้งระบบไม่มีส่วนไหนใช้กล้องแล้ว จึงไม่ต้องตั้ง https

ใบรับรองเป็นแบบ self-signed เบราว์เซอร์จะเตือนครั้งแรก กด "ไปต่อ" ได้

## พอร์ตที่ใช้

| พอร์ต | ใช้ทำอะไร |
| --- | --- |
| 4007 | API (Go) |
| 4008 | หน้าเว็บ — ตอน dev คือ vite ตอน production คือ nginx |
| 5432 | PostgreSQL (เปิดเฉพาะตอน dev) — ฐานข้อมูลชื่อ `line` |

เปลี่ยนพอร์ตได้ที่ `backend/.env` (ตัวแปร `PORT`) และ `frontend/vite.config.js`

## ขึ้น server จริงด้วย Docker

```bash
cp rewards.env.example rewards.env        # แก้รหัสผ่านและ JWT_SECRET
# สร้างใบรับรอง https ตามขั้นตอนใน certs/README.md
docker compose -f docker-compose.prod.yml up -d --build

# ครั้งแรกต้องสร้างตารางและใส่ข้อมูลตั้งต้น
docker compose -f docker-compose.prod.yml exec backend /app/rewards-migrate
docker compose -f docker-compose.prod.yml exec backend /app/rewards-seed
```

ผู้ใช้เข้าที่ `https://<IP ของเครื่อง server>:4008`

เปิดออกนอกเครื่องแค่พอร์ต 4008 เท่านั้น ส่วน backend กับ PostgreSQL คุยกันภายใน docker
(backend เปิดที่ `127.0.0.1:4007` ไว้ให้ไล่ปัญหาด้วย curl จากในเครื่อง server ได้)

| บทบาท | ช่องแรก | รหัสผ่าน |

## ข้อจำกัดที่ควรรู้

ระบบไม่ได้ใช้กล้องหรือ QR แล้ว
ที่มากับเบราว์เซอร์ ซึ่ง Chrome และ Edge บน Android รองรับ แต่ Safari บน iOS ยังไม่รองรับ
หน้าจะแสดงภาพกล้องได้ตามปกติ พร้อมบอกให้ใช้วิธีเลือกรูปจากอัลบั้มหรือกรอกรหัสแทน
ถ้าต้องรองรับ iOS ให้เพิ่มไลบรารีถอดรหัสฝั่งเบราว์เซอร์ เช่น `jsqr` หรือ `zxing-js`
การเปิดกล้องต้องรันผ่าน https หรือ localhost เท่านั้น

แบนเนอร์หน้าแรกอัปโหลดรูปได้แล้ว มีตัวครอปในตัว ไฟล์เก็บที่โฟลเดอร์ `backend/uploads`
และเสิร์ฟผ่านเส้นทาง `/uploads/` (ตอน dev vite ส่งต่อให้ ตอน production nginx ส่งต่อให้)
ขึ้น production ด้วย docker ไฟล์จะถูกเก็บใน volume ชื่อ `uploads` จึงไม่หายตอน deploy ใหม่

ของรางวัลก็อัปโหลดรูปได้เช่นกัน ใช้ตัวครอปตัวเดียวกันแต่ล็อกสัดส่วนไว้ที่ 4:3 ตามกรอบรูปในการ์ด
ส่วนรูปกิจกรรมยังเป็นบล็อกสีเทา ฐานข้อมูลมีคอลัมน์ `image_url` รออยู่แล้ว ต่อตัวอัปโหลดเดียวกันได้ทันที

เทมเพลตในแท็บ Systems Event เปิดปิดและเลือกช่องทางได้จริง แต่ตัวจับเวลาที่จะยิงแจ้งเตือนอัตโนมัติ
(เช่น เตือนก่อนคะแนนหมดอายุ) ยังต้องต่อ cron หรือ job scheduler เพิ่มเอง

## ข้อมูลตั้งต้น

`go run ./cmd/seed` **ไม่ได้ใส่ข้อมูลตัวอย่างแล้ว** สร้างให้เฉพาะสิ่งที่ระบบต้องมีจึงจะทำงานได้

| สิ่งที่สร้างให้ | เหตุผล |
| --- | --- |
| พนักงาน `1875` / `2962` และแอดมิน `admin` / `line` | บัญชีสำหรับเข้าใช้งานครั้งแรก |
| ระดับสมาชิก Member / Silver / Elite | ระบบใช้เกณฑ์คะแนนและตัวคูณจากตารางนี้ ถ้าว่างจะเลื่อนระดับไม่ได้ |
| ค่าตั้งระบบ และรายการแจ้งเตือนอัตโนมัติ | ระบบอ่านค่าจากตารางนี้ เช่น เกณฑ์วันหมดอายุคะแนน |
| เอกสารข้อกำหนดและนโยบาย PDPA | พนักงานต้องกดยอมรับก่อนเข้าใช้ครั้งแรก ถ้าไม่มีเอกสารจะเข้าใช้ไม่ได้ |

ของรางวัล กิจกรรม แบนเนอร์ และคำถามที่พบบ่อย **ว่างเปล่า** ให้ผู้ดูแลระบบกรอกเองจากหน้าแอดมิน
คำสั่งนี้สั่งซ้ำได้ ข้อมูลที่มีอยู่แล้วจะไม่ถูกเขียนทับ

## คะแนนและระดับสมาชิก

| ระดับ | เกณฑ์คะแนน | ตัวคูณ | คะแนนที่ต้องได้รับในรอบปีเพื่อคงระดับ |
| --- | --- | --- | --- |
| Member | 0 | x1.0 | — |
| Silver | 1,000 | x1.5 | 500 |
| Elite | 2,000 | x2.0 | 1,000 |

**ตัดยอดคะแนนประจำปี** ระบบทำให้เองเมื่อถึงวันที่ตั้งไว้ในหน้า System Settings
(ค่าเริ่มต้น 31 ธันวาคม) ผู้ดูแลไม่ต้องกดเอง แต่กดสั่งเองได้จากหน้าจัดการคะแนน

**คะแนนกลับเป็น 0 ทุกคนเท่ากัน** สิ่งที่ต่างกันคือระดับที่รักษาไว้ได้

| ระดับเดิม | คะแนนที่ได้รับในรอบปี | ระดับหลังรีเซ็ต | คะแนนหลังรีเซ็ต |
| --- | --- | --- | --- |
| Member | ไม่กำหนด | Member | 0 |
| Silver | ตั้งแต่ 500 | Silver | 0 |
| Silver | ต่ำกว่า 500 | Member | 0 |
| Elite | ตั้งแต่ 1,000 | Elite | 0 |
| Elite | ต่ำกว่า 1,000 | Silver | 0 |

เงื่อนไขคงระดับดูจาก **คะแนนที่ได้รับ** ไม่ใช่คะแนนคงเหลือ เพราะคนที่เข้าร่วมกิจกรรมและได้รับคะแนน
สม่ำเสมอคือคนที่มีส่วนร่วมกับระบบจริง (เดิมวัดจากคะแนนที่ใช้แลกของรางวัล เปลี่ยนมาวัดจากคะแนนที่ได้รับแทน)

ตัวตั้งเวลาอยู่ในโปรแกรม ตรวจทุกชั่วโมง และจำปีที่ตัดยอดไปแล้ว จึงไม่ตัดซ้ำ
แม้เปิดเซิร์ฟเวอร์หลายตัวหรือผู้ดูแลกดเองไปก่อนแล้ว

## หน้าวิเคราะห์ของผู้ดูแลระบบ

แท็บ **การวิเคราะห์** ในหน้าภาพรวม แบ่งเป็นสามส่วน — กิจกรรม คะแนน และของรางวัล

**ตัวกรองสามตัว** ช่วงวันที่ / แผนก / ระดับสมาชิก มีผลกับทุกบล็อกในหน้า

ช่วงวันที่เลือกได้ **เดือนนี้ / ปีนี้ / กำหนดเอง** แบบกำหนดเองจะมีช่องเลือกปี (พ.ศ.)
และเดือนเริ่มถึงเดือนจบโผล่ขึ้นมา เลือกเดือนจบก่อนเดือนเริ่มระบบสลับให้เอง

**โดนัทความถี่การเข้าร่วมกดดูรายชื่อได้** กดที่ชิ้นบนวงกลมหรือที่รายการข้าง ๆ
จะเปิดตารางบอกว่าใครอยู่ในช่วงนั้นบ้าง พร้อมแผนก ตำแหน่ง ระดับ และจำนวนครั้งที่เข้าร่วม
ให้กดได้สองที่เพราะชิ้นเล็ก ๆ บนวงกลมกดยาก โดยเฉพาะบนมือถือ
ช่วงที่มีประโยชน์ที่สุดคือ **0 ครั้ง** เพราะเป็นกลุ่มที่ต้องตามต่อ

## จัดการพนักงาน

**ช่องที่ต้องกรอกมีสามช่อง** รหัสพนักงาน · รหัสผ่าน · ชื่อ - สกุล ที่เหลือกรอกทีหลังได้

ฟอร์มเรียงเป็นสองคอลัมน์ รหัสพนักงานคู่กับรหัสผ่าน ชื่อคู่กับอีเมล เบอร์โทรคู่กับวันเกิด
อีเมลไม่บังคับแล้ว คนที่ไม่มีอีเมลเก็บเป็นค่าว่างในฐานข้อมูล จึงเพิ่มหลายคนได้โดยไม่ชนกัน

ช่องรหัสผ่านอยู่ถัดจากรหัสพนักงาน แสดงเป็นตัวอักษรปกติไม่ปิดเป็นจุด
เพราะผู้ดูแลต้องอ่านแจ้งพนักงาน ควรให้พนักงานเปลี่ยนเองหลังเข้าใช้ครั้งแรก
ตอนแก้ไขเว้นว่างคือไม่เปลี่ยนรหัสเดิม การเปลี่ยนรหัสผ่านถูกบันทึกใน audit log
แยกจากการแก้ข้อมูลทั่วไป

**ปุ่ม Export** ได้ไฟล์ `รายชื่อพนักงาน.xlsx` คอลัมน์
ลำดับ · รหัสพนักงาน · ชื่อ - นามสกุล · แผนก · ตำแหน่ง · สาขา · ระดับสมาชิก
เรียงตามรหัสพนักงานจากน้อยไปมาก ใช้ตัวเทียบแบบรู้จักตัวเลข
รหัส 9 จึงมาก่อน 10 ไม่ใช่เรียงแบบข้อความที่ 10 มาก่อน 9

ไฟล์**ได้ครบทุกคนตามตัวกรองที่ตั้งไว้ ไม่ติดการแบ่งหน้า** กรองเฉพาะแผนกหนึ่งไว้
ก็จะได้ไฟล์ของแผนกนั้นครบทุกคน ไม่ใช่เฉพาะที่เห็นบนหน้าจอ

เป็นไฟล์ .xlsx จริง ไม่ใช่ CSV เปลี่ยนนามสกุล จึงไม่มีกล่องเตือนตอนเปิด
เขียนเองใน `frontend/src/lib/xlsx.js` แทนการใช้ไลบรารีที่หนักเกือบ 1 MB

## เช็กอินกิจกรรมและรับของรางวัล

### เช็กอินกิจกรรม

1. พนักงานแจ้งรหัสพนักงานกับผู้ดูแล
2. ผู้ดูแลเปิดหน้าจัดการกิจกรรม กดปุ่ม **เช็คอิน** ที่แถวของกิจกรรมนั้น
3. กรอกรหัสพนักงานแล้วกดยืนยัน
4. ระบบบันทึกการเข้าร่วมและเพิ่มคะแนนให้อัตโนมัติ พร้อมคูณตัวคูณตามระดับ

เช็กอินซ้ำไม่ได้

**คนที่ไม่ได้ลงทะเบียนล่วงหน้าแต่มาหน้างาน เช็กอินให้ได้** ระบบทำเป็นสองจังหวะ

1. กรอกรหัสแล้วกดยืนยัน ระบบเห็นว่ายังไม่ได้ลงทะเบียน จึงคืนชื่อมาให้ตรวจก่อน ยังไม่บันทึกอะไร
2. ผู้ดูแลเทียบชื่อกับคนที่อยู่ตรงหน้า ถ้าตรงก็กด **เช็กอินแบบหน้างานให้เลย**
   ระบบบันทึกเป็นผู้เข้าร่วมและให้คะแนนเหมือนคนที่ลงทะเบียนมาปกติ

ที่ไม่ให้เช็กอินทันทีในจังหวะเดียว เพราะถ้าพิมพ์รหัสผิดไปตรงกับคนอื่น
คนที่ไม่ได้มางานจะได้คะแนนฟรีโดยไม่มีใครรู้ การให้ดูชื่อก่อนใช้เวลาเพิ่มแค่แตะเดียว

คนที่เช็กอินแบบหน้างานถูกทำเครื่องหมายไว้ มีป้าย **หน้างาน** ในรายชื่อผู้ลงทะเบียน
และบันทึกใน audit log ด้วย จะได้แยกออกว่าใครลงทะเบียนมาก่อนและใครมาหน้างาน

### รับของรางวัล

1. พนักงานกดแลกของรางวัลในระบบ หน้าจอบอกให้ไปติดต่อรับของที่ฝ่าย GA&ER
2. พนักงานไปติดต่อรับของที่ฝ่าย
3. ผู้ดูแลเปิดหน้าจัดการของรางวัล แท็บรายการแลก ตรวจชื่อพนักงานและรายการให้ตรงกัน
4. กด **ยืนยันรับของ** สถานะเปลี่ยนเป็นรับแล้วและแจ้งเตือนพนักงาน

ฝั่งพนักงานไม่มี QR แล้ว รายการที่รอรับจะมีข้อความบอกไว้ว่าไปรับได้ที่ไหน

ยืนยันซ้ำไม่ได้ ระบบจะบอกว่ารายการนี้ถูกยืนยันไปแล้ว

## รูปกิจกรรม

ฟอร์มสร้างและแก้ไขกิจกรรมมีช่องใส่รูปอยู่ล่างสุด ครอปดูก่อนอัปโหลดได้
สัดส่วน 2.8:1 (1120×400) ให้ตรงกับกรอบรูปในการ์ดกิจกรรมฝั่งพนักงาน

ส่งค่าว่างมาคือตั้งใจลบรูปทิ้ง ส่วนการแก้ไขช่องอื่นโดยไม่แตะรูป รูปเดิมจะอยู่เหมือนเดิม

## กิจกรรมแบบโหวต

กิจกรรมประเภท "โหวต" ตั้งตัวเลือกให้พนักงานเลือกได้ (เช่น ปลายทางทริปประจำปี)
แต่ละตัวเลือกมีชื่อและคำอธิบายสั้น ๆ จัดลำดับได้จากฟอร์มสร้างกิจกรรม

พนักงานต้องเลือกหนึ่งตัวเลือกก่อนกดยืนยัน โหวตได้ครั้งเดียวและแก้ไม่ได้
หลังโหวตแล้วจะเห็นว่าตัวเองเลือกอะไรและแต่ละตัวเลือกมีกี่โหวต

**ตัวเลือกที่มีคนโหวตแล้วจะลบไม่ได้** ทั้งจากหน้าจอและจากฝั่งเซิร์ฟเวอร์
เพื่อไม่ให้ผลโหวตที่บันทึกไว้หายไป ส่วนตัวเลือกที่ยังไม่มีใครเลือกลบได้ตามปกติ

## รายชื่อผู้ลงทะเบียนและใบลงชื่อ

หน้าจัดการกิจกรรมมีปุ่ม **รายชื่อ** ในทุกแถว เปิดดูผู้ลงทะเบียนทั้งหมดได้
พร้อมปุ่มดาวน์โหลดใบลงชื่อเป็น PDF สำหรับใช้หน้างาน

ตารางบนหน้าจอกับใบลงชื่อใช้คอลัมน์คนละชุดโดยตั้งใจ

| | คอลัมน์ |
| --- | --- |
| บนหน้าจอ | ลำดับ · รหัสพนักงาน · ชื่อ - นามสกุล · แผนก · ตำแหน่ง · สาขา · สถานะ (กิจกรรมโหวตมีตัวเลือกที่โหวตเพิ่ม) |
| ใบลงชื่อ PDF | ลำดับ · รหัส · ชื่อ-สกุล · แผนก · **ลงชื่อ** (ช่องว่างให้เซ็นด้วยปากกา) |

ใบลงชื่อตัดคอลัมน์ที่ไม่จำเป็นออก เพื่อเหลือที่ให้ช่องลงชื่อกว้างพอเซ็นจริง
กิจกรรมที่ยังไม่มีผู้ลงทะเบียนก็ดาวน์โหลดได้ จะได้ใบเปล่า 15 แถวไว้ให้คนมาหน้างานเขียนชื่อเอง

**ตารางบนหน้าจอมีช่องค้นหา** พิมพ์รหัสพนักงานหรือชื่อก็ได้ เรียงตามแผนกแล้วชื่อ
ส่วน**ใบลงชื่อเรียงตามรหัสพนักงานจากน้อยไปมาก** เพราะหน้างานหาคนด้วยรหัสเป็นหลัก
ใช้ตัวเทียบแบบรู้จักตัวเลข รหัส 9 จึงมาก่อน 10 ไม่ใช่เรียงแบบข้อความที่ 10 มาก่อน 9

ไฟล์ที่ดาวน์โหลด**ได้รายชื่อครบเสมอ ไม่ขึ้นกับคำค้นบนหน้าจอ** เพราะใบลงชื่อหน้างาน
ต้องมีทุกคน ไม่ใช่เฉพาะคนที่ผู้ดูแลกำลังค้นหาอยู่

### เรื่องภาษาไทยใน PDF

**ต้องฝังฟอนต์ไทยไปกับไฟล์** (Sarabun จาก Google Fonts สัญญาอนุญาต SIL OFL
ย่อเหลือเฉพาะอักขระที่ใช้ จาก 90 KB เหลือ 34 KB) ฟอนต์มาตรฐานของ PDF ไม่มีอักขระไทย

**วรรณยุกต์ที่ตามหลังสระบนต้องยกตำแหน่งเอง** คำว่า "ชื่อ" จะออกมาเป็น "ชือ" ถ้าไม่ทำ
เพราะฟอนต์วางวรรณยุกต์ให้ถูกที่ด้วยตาราง GPOS ซึ่งเป็นงานของตัวจัดเรียงอักษร
ตัวสร้าง PDF ไม่ได้ทำขั้นตอนนั้น มันวาดทีละตัวตามลำดับที่ได้รับ
วรรณยุกต์มีความกว้างศูนย์จึงถูกวาดทับสระที่อยู่ก่อนหน้าจนมองไม่เห็น

วิธีแก้อยู่ใน `frontend/src/lib/pdfThai.js` — วาดข้อความโดยเอาวรรณยุกต์ที่มีปัญหาออกก่อน
แล้ววาดซ้อนกลับเข้าไปโดยยกให้สูงขึ้นพ้นสระ ทำได้เพราะวรรณยุกต์กว้างศูนย์
การถอดออกจึงไม่ทำให้ตัวอื่นเลื่อน ส่วนวรรณยุกต์ที่ตามหลังพยัญชนะเฉย ๆ อยู่ถูกที่อยู่แล้ว

### ขนาดไฟล์ที่ส่งให้เบราว์เซอร์

ตัวสร้าง PDF ถูกแยกเป็นไฟล์ต่างหาก โหลดเฉพาะตอนผู้ดูแลกดดาวน์โหลด
พนักงานทั่วไปจึงไม่ต้องแบกไปด้วยทุกครั้งที่เปิดแอป

`npm run build` แยกไฟล์แบบนี้ ส่วน `npm run build:test` รวมเป็นไฟล์เดียวแบบ iife
ใช้เฉพาะตอนรันชุดทดสอบ เพราะเครื่องมือทดสอบรันโมดูล ES ไม่ได้

**ระดับขั้นต่ำ** ตั้งได้ว่าของรางวัลชิ้นนี้ต้องเป็นสมาชิกระดับไหนขึ้นไปจึงแลกได้
พนักงานระดับต่ำกว่ายังเห็นของรางวัลอยู่ แต่รูปจะถูกคลุมด้วยกุญแจและปุ่มเปลี่ยนเป็น
"ปลดล็อกเมื่อถึง …" ฝั่งเซิร์ฟเวอร์ตรวจซ้ำอีกชั้น ต่อให้ยิงตรงมาที่ API ก็แลกไม่ได้

**ช่วงเวลาแลก** ตั้งวันเริ่มและวันสิ้นสุดได้ สำหรับของรางวัลกิจกรรมพิเศษ
ของที่มีกำหนดจะมีป้าย "กิจกรรมพิเศษ" และนับถอยหลัง "เหลือเวลาแลกอีก N วัน"
**พ้นกำหนดแล้วระบบซ่อนจากหน้าพนักงานเองทันที ไม่ต้องรอผู้ดูแลปิด** และแลกไม่ได้
ส่วนหน้าแอดมินยังเห็นครบทุกชิ้นพร้อมสถานะ live / scheduled / expired

## หลายภาษา (ฝั่งพนักงานเท่านั้น)

ฝั่งพนักงานรองรับ **ไทย / English / 日本語** เปลี่ยนได้จากปุ่มโลกมุมซ้ายบนของหน้าหลัก
และที่มุมขวาบนของหน้าเข้าสู่ระบบ เลือกแล้วเปลี่ยนทันทีและจำไว้ให้ครั้งถัดไป
ค่าเริ่มต้นคือภาษาไทย

| ไฟล์ | หน้าที่ |
| --- | --- |
| `frontend/src/lib/i18n.jsx` | ตัวจัดการภาษาและฟังก์ชัน `t()` |
| `frontend/src/lib/locales/th.js` | ข้อความภาษาไทย ใช้เป็นต้นฉบับ |
| `frontend/src/lib/locales/en.js` · `ja.js` | คำแปล ต้องมีคีย์ครบเท่าไฟล์ไทย |
| `frontend/src/lib/format.js` | วันที่และเวลา ไทยใช้ พ.ศ. อังกฤษกับญี่ปุ่นใช้ ค.ศ. |

เพิ่มข้อความใหม่ให้ใส่คีย์ในทั้งสามไฟล์ แล้วเรียกด้วย `t('ชื่อคีย์')`
ตัวแปรในข้อความเขียนเป็น `{{ชื่อตัวแปร}}` แล้วส่งค่าเป็นอาร์กิวเมนต์ที่สอง

### ข้อมูลที่ผู้ดูแลกรอกเองก็แปลได้

ชื่อของรางวัล ชื่อกิจกรรม สิทธิประโยชน์ FAQ ข้อกำหนด และชื่อแบนเนอร์ กรอกคำแปลได้ 3 ภาษา
**ผู้ดูแลระบบกรอกภาษาไทยอย่างเดียว** ฟอร์มในหน้าจัดการไม่มีแท็บเลือกภาษา

- ภาษาไทยเก็บในคอลัมน์ปกติของตาราง (`title`, `name`, ...)
- คอลัมน์ `translations` สำหรับเก็บคำแปลยังอยู่ และ API ยังเอาคำแปลมาทับให้ถ้ามี
  แต่ตอนนี้ไม่มีหน้าจอให้กรอก จึงมีคำแปลเฉพาะที่ระบบใส่มาให้ (ระดับสมาชิกและเอกสารข้อกำหนด)
- **ช่องไหนไม่มีคำแปล หน้าเว็บจะแสดงภาษาไทยแทน** ผู้ใช้จึงไม่เจอช่องว่าง
- ถ้าภายหลังอยากกรอกคำแปลเอง เพิ่มแท็บกลับมาที่ `frontend/src/components/TranslatedFields.jsx`
  ไฟล์เดียว ฝั่งหลังบ้านรองรับอยู่แล้ว

หน้าเว็บฝั่งพนักงานส่งภาษาที่เลือกไปกับทุกคำขอ (`?lang=en`) และ API เอาคำแปลมาทับให้
ตารางที่รองรับ: `events`, `rewards`, `tiers`, `faqs`, `policies`, `banners`

**ยังไม่แปล** ชื่อของรางวัล ชื่อกิจกรรม คำถามที่พบบ่อย และข้อความในประวัติคะแนนกับการแจ้งเตือน เพราะถูกสร้างเป็นภาษาไทยตอนที่เกิดรายการ
และเก็บเป็นข้อความสำเร็จรูปในฐานข้อมูล ถ้าต้องการให้แปลด้วย ต้องเปลี่ยนไปเก็บเป็นรหัสเหตุการณ์
แล้วประกอบข้อความตอนแสดงผลแทน **ฝั่งแอดมินทั้งหมดยังเป็นภาษาไทยอย่างเดียว**

## เส้นทางไม่ขึ้นในแถบที่อยู่

แอปเก็บเส้นทางไว้ในหน่วยความจำแทนการเขียนลงแถบที่อยู่ ผู้ใช้จึงเห็นแค่
`http://เครื่อง:4008` ตลอดการใช้งาน ไม่มี `/login` หรือ `/rewards` ต่อท้าย

ยังรับเส้นทางที่พิมพ์มาตอนเปิดครั้งแรก เผื่อมีลิงก์เดิมที่เคยส่งต่อกันไว้
แต่พอกดใช้งานต่อแล้วที่อยู่จะไม่เปลี่ยนอีก

**ข้อแลกเปลี่ยนที่ควรรู้** ปุ่มย้อนกลับของเบราว์เซอร์จะออกจากเว็บแทนที่จะถอยกลับหน้าก่อนหน้า
และส่งลิงก์เข้าหน้าใดหน้าหนึ่งให้คนอื่นไม่ได้ ทุกหน้ามีปุ่มย้อนกลับของแอปเองอยู่แล้ว
ถ้าอยากได้เส้นทางกลับมา เปลี่ยน `MemoryRouter` เป็น `BrowserRouter` ใน `frontend/src/main.jsx`

## การรองรับมือถือ

**ฝั่งผู้ดูแลระบบใช้บนมือถือได้ทุกหน้า** จอเล็กไม่มีเมนูข้าง แต่มีแถบล่างสี่เมนูที่ใช้บ่อย
(ภาพรวม สแกน กิจกรรม ของรางวัล) และปุ่มเมนูที่เปิดรายการทั้งหมดรวมถึงหน้าที่อยู่ในกลุ่ม
ปุ่มประจำหน้าย้ายลงบรรทัดถัดไปบนจอเล็ก จะได้ไม่เบียดกับชื่อหน้า
ตารางทุกหน้าเลื่อนแนวนอนได้ในตัวเอง ไม่ทำให้ทั้งหน้าเลื่อนตาม


- เลย์เอาต์ทุกหน้าเขียนแบบ mobile-first
- เผื่อระยะ `env(safe-area-inset-*)` ให้เครื่องที่มีรอยบากและแถบล่าง
- ปุ่มและช่องกรอกสูงอย่างน้อย 44px ฟอนต์ช่องกรอก 15px เพื่อไม่ให้ iOS ซูมเอง
- ชิปตัวกรองเลื่อนแนวนอนได้ ซ่อนแถบเลื่อนไว้
- มีขอบโฟกัสที่มองเห็นชัดสำหรับคนใช้คีย์บอร์ด และเคารพ `prefers-reduced-motion`
- ตารางฝั่งแอดมินเลื่อนแนวนอนในกรอบของตัวเอง หน้าเว็บจึงไม่เลื่อนออกด้านข้าง

## หมายเหตุการพัฒนา

- การแลกของรางวัลและการเช็คอินทำงานใน transaction เดียว ล็อกแถวด้วย `FOR UPDATE`
  เพื่อกันคะแนนติดลบและกันแลกของเกินสต็อกเมื่อมีคนกดพร้อมกัน
- ทุกการได้และใช้คะแนนถูกบันทึกลง `point_transactions` ส่วน `users.points` เป็นยอดสรุป
  ตรวจยอดย้อนหลังได้จากตารางเดินบัญชี
- backend ใช้ `net/http` ของ Go ล้วน ไม่ได้ใช้เฟรมเวิร์ก เส้นทางทั้งหมดลงทะเบียนกับ `ServeMux`
  ของ Go 1.22 ที่ระบุ method และ path parameter ได้ในตัว
- รหัสผ่านแฮชด้วย PBKDF2-HMAC-SHA256 (210,000 รอบ ตามที่ OWASP แนะนำ) ซึ่งประกอบจาก
  `crypto/hmac` กับ `crypto/sha256` ที่มากับ Go จึงไม่ต้องพึ่ง `golang.org/x/crypto`
  ทำให้ build ได้แม้ในเครือข่ายที่ดึงโมดูลนั้นไม่ได้
- JWT เป็น HS256 มาตรฐานเดียวกับฝั่ง Node จึงใช้แทนกันได้
- คะแนนที่ได้จากกิจกรรมถูกคูณด้วย `multiplier` ของระดับที่พนักงานอยู่ ณ ตอนนั้น
  (Member x1.0, Silver x1.5, Elite x2.0 ตามค่าเริ่มต้น) ทุกจุดที่จ่ายคะแนนเรียกผ่าน `awardPoints`
  ตัวเดียวกัน จึงไม่มีทางที่บางเส้นทางจะลืมคูณ ส่วนการปรับคะแนนด้วยมือของผู้ดูแลไม่คูณ
- ระดับสมาชิกเลื่อนขึ้นอัตโนมัติทันทีที่คะแนนถึงเกณฑ์ และมีแจ้งเตือนให้พนักงาน
  นอกจากตอนได้คะแนนแล้ว ระบบยังตรวจซ้ำตอนเข้าสู่ระบบและตอนเปิดหน้าแรก
  เผื่อคะแนนถูกแก้จากทางอื่น เช่น แก้ตรงในฐานข้อมูลหรือย้ายข้อมูลมาจากระบบเดิม
  การได้คะแนนและการแลกของรางวัล**เลื่อนขึ้นอย่างเดียว ไม่ลดระดับ** เพราะคะแนนจะลดทุกครั้งที่แลกของ
  ถ้าลดตามคะแนนคงเหลือ พนักงานจะหลุดระดับทันทีที่ใช้คะแนน
- ส่วน**การปรับคะแนนด้วยมือของผู้ดูแลระบบจะคิดระดับใหม่ทั้งขึ้นและลง** เพราะเป็นการแก้ข้อมูล
  โดยตั้งใจ ผลลัพธ์จึงควรสะท้อนคะแนนที่แก้ทันที (เช่น 2,100 ปรับลง 200 เหลือ 1,900 จะกลับเป็น Member)
- ทุกการกระทำสำคัญของผู้ดูแลระบบถูกบันทึกลง `audit_logs` ผ่านตัวช่วย `logAudit`
  ซึ่งตั้งใจให้ล้มเหลวเงียบ ๆ เพราะการบันทึกไม่ควรทำให้งานหลักพัง
- เกณฑ์ระดับสมาชิกและค่าตั้งต่าง ๆ อ่านจากตาราง `tiers` และ `settings` ไม่ได้ฝังไว้ในโค้ด
  แอดมินแก้แล้วมีผลกับฝั่งพนักงานทันที
- โทเค็นเก็บใน localStorage เพื่อความง่ายของเดโม ก่อนขึ้นใช้งานจริงควรย้ายไป httpOnly cookie
  และเพิ่ม rate limit ที่เส้นทางล็อกอิน

## ขึ้น production แบบไม่ใช้ Docker

```bash
cd frontend && npm run build      # ได้ไฟล์ static ที่ frontend/dist
cd ../backend && go build -o rewards . && ./rewards   # API ที่พอร์ต 4007
```

เอา `frontend/dist` ไปเสิร์ฟด้วย nginx โดยใช้ `frontend/nginx.prod.conf` เป็นต้นแบบ
(แก้ `proxy_pass` จาก `http://backend:4007` เป็น `http://127.0.0.1:4007`)

ถ้าหน้าเว็บกับ API อยู่คนละ origin ให้ตั้ง `VITE_API_URL` ก่อน build และตั้ง `CLIENT_ORIGIN`
ฝั่งเซิร์ฟเวอร์ให้ตรงกับโดเมนหน้าเว็บ อย่าลืมเปลี่ยน `JWT_SECRET` ด้วย

## เจอปัญหาตอนรัน

### หน้าเว็บไม่ขึ้นเลย

- เปิดให้ถูก protocol — `npm run dev` คือ **http** ไม่ใช่ https
  เปิดจากมือถือให้ใช้ `npm run dev:https` ซึ่งพิมพ์ URL ของวงแลนให้ดูด้วย
  และส่ง argument ต่อให้ vite ได้ เช่น `npm run dev:https -- --host 192.168.1.50`
  ถ้าพิมพ์ `https://localhost:4008` ขณะรันโหมด http หน้าจะว่างเปล่าหรือขึ้น error ทันที
- ดูบรรทัดที่ vite พิมพ์ออกมา มันบอก URL ที่ถูกต้องอยู่แล้ว
- ถ้าขึ้น `Port 4008 is already in use` แปลว่ามีอะไรจองพอร์ตอยู่
  หาแล้วปิดด้วย `netstat -ano | findstr :4008` แล้ว `taskkill /PID <เลข> /F`
- ถ้าขึ้น `Cannot find package` แปลว่ายังไม่ได้ `npm install` ในโฟลเดอร์นั้น

### หน้าเว็บขึ้น แต่ล็อกอินไม่ได้ / ข้อมูลไม่มา

แปลว่า backend หรือฐานข้อมูลมีปัญหา ไล่ตามนี้

```bash
cd backend
go run ./cmd/check            # บอกเลยว่าติดตรงไหน
```

- `ต่อ PostgreSQL ไม่ได้` → PostgreSQL ยังไม่ได้เปิด หรือพอร์ตไม่ตรง
- `ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง` → แก้ `DATABASE_URL` ใน `backend/.env`
- `ยังไม่มีฐานข้อมูลชื่อนี้` → สั่ง `go run ./cmd/migrate` ระบบจะสร้างให้เอง
- `บัญชีนี้ไม่มีสิทธิ์สร้างฐานข้อมูล` → ใช้บัญชี `postgres` หรือสั่ง `ALTER ROLE ชื่อผู้ใช้ CREATEDB;`
- `ยังไม่มีตาราง` → ปกติ `go run .` สร้างให้เองอยู่แล้ว ถ้ายังไม่มีให้สั่ง `go run ./cmd/migrate`

เวลาเปิด backend มันจะพิมพ์สถานะฐานข้อมูลให้ดูทุกครั้ง ถ้าเห็นบรรทัดขึ้นต้นด้วย `⚠`
แปลว่าต่อฐานข้อมูลไม่ได้ ตัว API จะยังเปิดอยู่แต่ทุกหน้าจะดึงข้อมูลไม่ได้

### ตรวจว่า backend ทำงานจริงไหม

```bash
curl http://localhost:4007/api/health
```

ควรได้ `{"ok":true}` ถ้าไม่ได้แปลว่า backend ยังไม่ได้รันหรือรันคนละพอร์ต

# ส่วนที่เพิ่มเข้ามารอบนี้

## 1. รองรับสามภาษาเต็มรูปแบบ (ไทย / อังกฤษ / ญี่ปุ่น)

### ข้อความในโปรแกรม

อยู่ที่ `frontend/src/lib/locales/{th,en,ja}.js` ทั้งสามไฟล์ต้องมีคีย์ครบเท่ากันเสมอ
ตรวจได้ด้วยคำสั่งนี้ ถ้าขึ้นอาเรย์ว่างทั้งคู่แปลว่าครบ

```bash
cd frontend
node -e "(async()=>{const th=(await import('./src/lib/locales/th.js')).default,en=(await import('./src/lib/locales/en.js')).default,ja=(await import('./src/lib/locales/ja.js')).default;const k=Object.keys(th);console.log('ขาดใน en:',k.filter(x=>!(x in en)));console.log('ขาดใน ja:',k.filter(x=>!(x in ja)));})()"
```

เปลี่ยนภาษาแล้วมีผลทันทีโดยไม่โหลดหน้าใหม่ หน้าที่ดึงข้อความซึ่งผู้ดูแลกรอกไว้
จะใส่ `lang` ไว้ใน dependency ของ `useEffect` จึงดึงข้อมูลชุดภาษาใหม่ให้เอง

### ข้อความที่ผู้ดูแลกรอก — แปลให้อัตโนมัติ

**ผู้ดูแลกรอกภาษาไทยอย่างเดียว** ระบบแปลเป็นอังกฤษและญี่ปุ่นให้เองเบื้องหลัง
ครอบคลุมของรางวัล กิจกรรม ตัวเลือกโหวต แบนเนอร์ ประกาศ/แจ้งเตือน FAQ
ข้อกำหนด ระดับสมาชิก และหัวข้อลงทะเบียน

คำแปลเก็บในคอลัมน์ `translations` ของแต่ละตาราง รูปแบบ

```json
{
  "en":   { "title": "..." },
  "ja":   { "title": "..." },
  "_src": { "title": "<ลายนิ้วมือของข้อความไทย>" },
  "_meta": { "triedAt": "<เวลาที่ลองแปลแล้วไม่สำเร็จ>" }
}
```

`_src` คือกลไกของข้อกำหนด *"อัปเดตคำแปลเมื่อมีการแก้ไข"* — แก้ข้อความไทยเมื่อไหร่
ลายนิ้วมือจะไม่ตรง ระบบจึงรู้เองว่าต้องแปลช่องนั้นใหม่ ช่องที่ไม่ได้แก้จะไม่ถูกแตะ
คำแปลที่ผู้ดูแลแก้เองด้วยมือจึงอยู่คงเดิมจนกว่าต้นฉบับภาษาไทยจะเปลี่ยน

ตัวแปลทำงานเป็นรอบทุก `TRANSLATE_INTERVAL` วินาที (ค่าเริ่มต้น 60) ไม่ได้แปลตอนกดบันทึก
เหตุผลคือผู้ดูแลไม่ต้องรอบริการแปลตอบ ข้อมูลเก่าถูกไล่แปลให้เองโดยไม่ต้องสั่ง
และบริการแปลล่มก็ไม่กระทบการใช้งาน

**จัดการได้ที่** `ตั้งค่าระบบ → คำแปลหลายภาษา` ดูความคืบหน้า สั่งแปลทันที
และแก้คำแปลที่ไม่ถูกใจเองได้รายช่อง

### เลือกบริการแปล

ตั้งที่ `backend/.env` (หรือ `rewards.env` ตอนรันด้วย Docker)

| ค่า | ใช้เมื่อไหร่ |
| --- | --- |
| `libre` | **แนะนำที่สุด** LibreTranslate ที่ติดตั้งเองในวงแลน ข้อมูลไม่ออกนอกองค์กร |
| `auto` | ค่าเริ่มต้น มี `TRANSLATE_URL` ก็ใช้ LibreTranslate ไม่มีก็ลองออกเน็ต |
| `google` | จุดเชื่อมต่อสาธารณะ ไม่ต้องใช้กุญแจ เหมาะกับงานภายในปริมาณไม่มาก |
| `offline` | ไม่เรียกเน็ตเลย ใช้คลังคำในตัวโปรแกรมอย่างเดียว |

เปิด LibreTranslate ในวงแลน

```bash
docker compose -f docker-compose.prod.yml --profile translate up -d
# แล้วตั้ง TRANSLATE_URL=http://translate:5000 ใน rewards.env
```

### เมื่อออกเน็ตไม่ได้

ระบบมีคลังคำในตัวโปรแกรม (`backend/translate/glossary.go`) เป็นตัวสำรอง
**แต่จะใช้ผลลัพธ์ก็ต่อเมื่อแปลได้ครอบคลุมอย่างน้อย 85% ของตัวอักษรไทย**

เกณฑ์นี้สำคัญมาก ถ้าไม่มี ประโยคยาวจะออกมาเป็นลูกผสมแบบ
`"รับ points addขึ้น 1.5 เท่า have rewardให้ redeem"` ซึ่งอ่านไม่รู้เรื่องทั้งสองภาษา
และแย่กว่าไม่แปลเลย เมื่อไม่ถึงเกณฑ์ระบบจะแสดงภาษาไทยต้นฉบับไว้
ผู้ใช้ต่างชาติเห็นภาษาไทยยังคัดลอกไปแปลเองได้ แต่เห็นข้อความพังทำอะไรไม่ได้

ข้อความสั้นอย่างชื่อหมวดหมู่หรือชื่อของรางวัลมักผ่านเกณฑ์และแปลออกมาสะอาด

## 2. สรุปการลงทะเบียน / แบบสำรวจ และไฟล์ Excel

เมนู `สรุปการลงทะเบียน` ในฝั่งผู้ดูแลระบบ

### ใครเห็นอะไร

role `ga` สำหรับฝ่ายธุรการ **เห็นข้อมูลเท่ากับผู้ดูแลระบบ รวมถึงชื่อพนักงาน**
ต่างกันที่แก้ไขข้อมูลไม่ได้

| สิ่งที่ทำได้ | admin | ga |
| --- | :---: | :---: |
| ยอดรวมรายแผนก (กี่คน เหลือกี่ %) | ✓ | ✓ |
| รายชื่อคนที่ยังไม่ได้ทำ | ✓ | ✓ |
| คำตอบและความคิดเห็น | ✓ | ✓ |
| รายชื่อผู้ลงทะเบียนของแต่ละกิจกรรม | ✓ | ✓ |
| สร้าง / แก้ไข / ลบ / ส่งแจ้งเตือน | ✓ | ✗ |
| จัดการพนักงาน ของรางวัล คะแนน ฯลฯ | ✓ | ✗ |

การกันสิทธิ์ทำที่เซิร์ฟเวอร์ ไม่ใช่แค่ซ่อนปุ่มที่หน้าจอ — เส้นทางที่แก้ไขข้อมูล
ตอบ 403 ให้ role `ga` ทุกเส้นทาง

#### ข้อยกเว้น: หัวข้อแบบไม่ระบุตัวตน

หัวข้อมีสวิตช์ *ไม่ระบุตัวตนผู้ตอบ* อยู่ **ค่าเริ่มต้นคือปิด** (เห็นชื่อ)

ถ้าเปิดสวิตช์นี้ คำตอบจะไม่มีชื่อผู้ตอบติดมาเลย **ไม่ว่าใครเป็นคนเรียกดู
รวมถึงผู้ดูแลระบบ** เพราะพนักงานเห็นข้อความแจ้งไว้บนหน้าจอก่อนกดส่ง
ระบบจึงต้องทำตามที่บอกไว้

ใช้เมื่อถามเรื่องที่คนจะตอบตรง ๆ ก็ต่อเมื่อไม่ต้องเปิดเผยตัว
เช่นความพึงพอใจต่อหัวหน้างาน ส่วนการลงทะเบียนทั่วไปให้ปิดไว้ตามค่าเริ่มต้น

ไม่ว่าสวิตช์จะเปิดหรือปิด **รายชื่อคนที่ยังไม่ได้ทำก็ดูได้เสมอ**
เพราะการรู้ว่าใครยังไม่ทำ ไม่ได้เปิดเผยว่าใครตอบอะไร

สร้างบัญชีฝ่ายธุรการได้โดยสร้างแอดมินตามปกติ แล้วสั่ง

```sql
UPDATE users SET role = 'ga' WHERE username = 'ชื่อผู้ใช้';
```

### ชื่อหัวข้อแก้ได้

ช่อง **ชื่อหัวข้อ** (เช่น `ข้อมูลพนักงานลงทะเบียน Line OA`) ถูกใช้เป็น
**หัวคอลัมน์กลางตารางในไฟล์ Excel** ด้วย เปลี่ยนที่หน้าเว็บแล้วไฟล์เปลี่ยนตามทันที
เหมือนกับหัวเรื่องบนสุด เลขรุ่นเอกสาร และข้อความกำกับจำนวนพนักงานมุมขวาบน

### ไฟล์ Excel ที่ดาวน์โหลด

วางคอลัมน์ตรงกับไฟล์ที่ใช้กันอยู่เดิม เอาไปวางแทนกันได้ทันที

```
Location | Section | Manpower | <ชื่อหัวข้อ>                              | Remark
                     number     Completed | Not Complete | Completion Rate
```

- ผสานเซลล์ชื่อสาขาให้คลุมทุกแถวของกลุ่มรวมแถว Total
- ตัวเลขเป็นตัวเลขจริง คอลัมน์ % เป็นรูปแบบเปอร์เซ็นต์ เอาไปคำนวณต่อได้เลย
- ครบ 100% พื้นเขียว ยังเหลือคนจะเป็นตัวเลขแดง
- มีแถว Total ของแต่ละสาขาและ Grand Total ท้ายสุด
- **ชีต `Not Complete` ใส่ให้เฉพาะตอนที่ผู้ดาวน์โหลดเป็นผู้ดูแลระบบ** ฝ่ายธุรการจะได้แค่ชีตสรุป

`Location` มาจากช่อง *สาขา* ของพนักงาน และ `Section` มาจากช่อง *แผนก*
จึงไม่ต้องกรอกข้อมูลซ้ำ ใช้ข้อมูลพนักงานที่มีอยู่แล้ว

ตัวสร้างไฟล์อยู่ที่ `frontend/src/lib/xlsxReport.js` (สมุดงานหลายชีตพร้อมรูปแบบ)
และ `frontend/src/lib/registrationReport.js` (ผังของรายงานนี้โดยเฉพาะ)
เขียน XML เองเหมือนเดิมเพื่อไม่ต้องลากไลบรารี xlsx ขนาดเกือบ 1 MB
และโหลดเฉพาะตอนกดปุ่มดาวน์โหลดเท่านั้น

### ความคืบหน้ารายแผนกของแต่ละกิจกรรม

เปิดได้จาก `จัดการกิจกรรม → รายชื่อ` ในหน้าต่างรายชื่อผู้ลงทะเบียนมีตาราง
*ความคืบหน้ารายแผนก* บอกว่าแต่ละแผนกมีกี่คน ลงทะเบียนแล้วกี่คน เหลือกี่คน กี่เปอร์เซ็นต์

ตัวเลขตั้งต้นจาก **พนักงานทั้งหมดที่ยังทำงานอยู่** ไม่ใช่จากคนที่ลงทะเบียนแล้ว
จึงบอก "เหลืออีกกี่คน" ได้จริง ไม่ใช่แค่ "มีกี่คนที่ลงทะเบียน"

ใช้ตัวนับตัวเดียวกับรายงานสรุป (`DepartmentProgress` ใน `controllers/surveys.go`)
ตัวเลขของสองหน้าจึงตรงกันเสมอ

### แจ้งเตือนคนที่ยังไม่ทำ

ปุ่ม `แจ้งเตือนคนที่ยังไม่ทำ` ส่งการแจ้งเตือนในแอปถึงทุกคนที่ยังไม่ได้ทำรายการนั้น
ใช้ร่วมกับการดาวน์โหลดชีต `Not Complete` ไปตามงานต่อได้

### ฝั่งพนักงาน

เมนู `สิ่งที่ต้องทำ` ในหน้าโปรไฟล์ รองรับทั้งการลงทะเบียน แบบสำรวจแบบเลือกตอบ
และช่องแสดงความคิดเห็น ตอบได้ครั้งเดียวต่อหัวข้อ และได้คะแนนถ้าตั้งไว้

ก่อนกดส่งจะมีข้อความบอกชัดว่าใครจะเห็นอะไร เพราะคนจะตอบตามจริง
ก็ต่อเมื่อรู้ว่าปลอดภัยที่จะตอบ

## 3. การอัปเกรดฐานข้อมูล

เดิมการเปลี่ยนโครงตารางต้องสั่ง `cmd/migrate` ซึ่ง **ล้างข้อมูลเดิมทิ้งทั้งหมด**
รอบนี้เพิ่มระบบต่อเติมแบบไม่ลบข้อมูลไว้ที่ `backend/db/migrations/`

- ไฟล์ SQL ถูกฝังไว้ในตัวโปรแกรมด้วย `embed` สั่งรันจากโฟลเดอร์ไหนก็หาเจอ
  และไฟล์ไบนารีที่ build แล้วเอาไปวางเครื่องอื่นได้เลย
- รันอัตโนมัติตอนเปิดเซิร์ฟเวอร์ จดไว้ในตาราง `schema_migrations` ว่ารันอะไรไปแล้ว
- ทุกไฟล์เขียนแบบรันซ้ำได้ (`IF NOT EXISTS`) และ **ห้ามลบหรือเขียนทับข้อมูลเดิม**

**อัปเกรดระบบที่ใช้งานอยู่ได้ด้วยการ deploy ทับอย่างเดียว ไม่ต้องเข้าไปสั่ง SQL เองที่เครื่อง server**

## 1. ประกาศข่าวสารที่ต้องกดรับทราบ

เมนู `ประกาศและเนื้อหา → ประกาศข่าวสาร`

พนักงานเข้าระบบมาแล้วถ้ามีประกาศที่ยังไม่ได้กดรับทราบ จะถูกแสดงทับทุกหน้าทันที
ปุ่ม **รับทราบข้อมูลข่าวสาร** จะกดได้ก็ต่อเมื่อเลื่อนอ่านลงมาจนสุดแล้วเท่านั้น

ระบบเก็บไว้ว่าใครกดเมื่อไหร่ ใช้เป็นหลักฐานว่าแจ้งแล้วจริง
ผู้ดูแลกด `ใครอ่านแล้ว` เพื่อดูความคืบหน้ารายแผนกและรายชื่อคนที่ยังไม่ได้กด

มีประกาศค้างหลายฉบับจะแสดงทีละฉบับเรียงจากเก่าไปใหม่

สองกรณีที่ตั้งใจดูแลไว้เป็นพิเศษ เพราะปล่อยไว้แล้วผู้ใช้จะติดอยู่ในหน้านั้น

- **เนื้อหาสั้นจนไม่มีอะไรให้เลื่อน** → ถือว่าอ่านครบทันที ปุ่มกดได้เลย
- **รูปประกอบโหลดเสร็จทีหลัง** ทำให้ความสูงเปลี่ยน → ใช้ `ResizeObserver` วัดใหม่
  ไม่งั้นผู้ใช้เลื่อนสุดแล้วแต่ปุ่มยังไม่ติด

ตั้งใจให้ต่างจากคะแนนปกติสามข้อ

- **ไม่คูณด้วยตัวคูณของระดับสมาชิก** ตั้งให้เท่าไหร่ได้เท่านั้น เพราะเป็นรางวัลเฉพาะกิจ
- **ไม่นำไปคิดระดับสมาชิก** ปรับคะแนนพิเศษจึงไม่ทำให้ใครเลื่อนหรือตกระดับ
- **ไม่ถูกตัดยอดตอนสิ้นปี** พร้อมคะแนนปกติ

ใช้งานได้สามที่

| ที่ | ทำอะไรได้ |
| --- | --- |
| สร้าง/แก้ไขกิจกรรม | ช่อง **คะแนนพิเศษ** จ่ายเพิ่มจากคะแนนปกติเมื่อเข้าร่วม |
| เพิ่ม/แก้ไขของรางวัล | เลือก **แลกด้วยคะแนนปกติ หรือ คะแนนพิเศษ** |
| ปรับคะแนน | เลือกได้ว่าจะปรับกระเป๋าไหน |

ของรางวัลชิ้นหนึ่งแลกด้วยกระเป๋าเดียว ไม่ผสมสองกระเป๋า
เพราะถ้าผสมแล้วพนักงานจะเดาไม่ออกว่าตัวเองจ่ายอะไรไปเท่าไหร่

ฝั่งพนักงานเห็นยอดทั้งสองกระเป๋าในหน้าคะแนนและหน้าของรางวัล
(แสดงกระเป๋าคะแนนพิเศษเฉพาะคนที่มี จะได้ไม่รกสำหรับคนที่ยังไม่เคยได้)
และประวัติคะแนนมีไอคอนกำกับว่าแต่ละรายการเป็นกระเป๋าไหน

## 3. สิทธิ์ปรับคะแนนตามตำแหน่งงาน

ปรับคะแนนได้เฉพาะ **ผู้ดูแลระบบ** หรือคนที่มีตำแหน่ง **Chief Engineer ขึ้นไป**
ซึ่งคือแปดตำแหน่งแรกของรายการ

```
Director → Co-General Manager → Assistant General Manager → Co-Manager
→ Manager → Assistant Manager → Specialist → Chief Engineer
```

ลำดับใน `Positions` (`backend/controllers/positions.go`) มีความหมายต่อสิทธิ์
**ห้ามเรียงใหม่ตามตัวอักษร**

ระบบอ่านตำแหน่งจากฐานข้อมูลทุกครั้งแทนที่จะฝังไว้ใน token
เพราะถ้าลดตำแหน่งใครลง สิทธิ์ต้องหายทันที ไม่ใช่รอ token หมดอายุอีกเจ็ดวัน
ทดสอบแล้วว่าเลื่อนหรือลดตำแหน่งแล้วมีผลทันทีโดยไม่ต้องล็อกอินใหม่

เส้นทาง `POST /api/admin/points/adjust` ใช้ `RequireReport` ไม่ใช่ `RequireAdmin`
แล้วให้ `CanAdjustPoints` ตัดสินอีกชั้น ถ้าใช้ `RequireAdmin` กติกาเรื่องตำแหน่ง
จะไม่มีผลกับใครเลย เพราะผู้ดูแลผ่านอยู่แล้วและคนอื่นถูกปฏิเสธตั้งแต่ชั้นแรก

## 4. ช่องเลือกตำแหน่งและแผนก

หน้าเพิ่ม/แก้ไขพนักงาน เปลี่ยนช่องตำแหน่งและแผนกเป็นช่องที่ **พิมพ์ค้นหาได้**
(`components/ComboBox.jsx`) มีตำแหน่ง 34 รายการและแผนก 30 รายการ
พิมพ์สองสามตัวอักษรแล้วเจอเลย ไม่ต้องเลื่อนหา

- คำที่ขึ้นต้นตรงกันขึ้นก่อน แล้วค่อยคำที่มีคำค้นอยู่ตรงกลาง
- เลื่อนด้วยลูกศรขึ้นลงและกด Enter เลือกได้
- ไม่มีในรายการให้เลือก **อื่นๆ (กรอกเอง)** แล้วพิมพ์
- **ค่าเก่าที่ไม่อยู่ในรายการจะเข้าโหมดพิมพ์เองอัตโนมัติ** ข้อมูลเดิมจึงไม่หายตอนเปิดฟอร์มแก้ไข

รายการดึงจาก `GET /api/admin/org-options` ก่อนเสมอ เพิ่มตำแหน่งใหม่ที่เซิร์ฟเวอร์
แล้วทุกเครื่องเห็นพร้อมกันโดยไม่ต้อง build ใหม่ ถ้าเรียกไม่สำเร็จจะใช้สำเนาใน
`frontend/src/lib/org.js` แทน ช่องเลือกจึงไม่เคยว่างเปล่า

เซิร์ฟเวอร์ยังส่งค่าที่เคยกรอกเองไว้มาต่อท้ายรายการมาตรฐาน
ผู้ดูแลจึงเลือกซ้ำได้โดยไม่ต้องพิมพ์ใหม่ทุกครั้ง

**แก้รายการตำแหน่ง/แผนกต้องแก้สองที่ให้ตรงกัน**
`backend/controllers/positions.go` และ `frontend/src/lib/org.js`

## สรุปข้อมูล และ Export Excel

หน้า `สรุปการลงทะเบียน` ที่เคยเป็นเมนูแยก **ถูกเอาออกแล้ว** เพราะข้อมูลซ้ำกับ
ตารางในหน้าต่างรายชื่อผู้ลงทะเบียนของแต่ละกิจกรรม

ตารางนั้นเปลี่ยนชื่อเป็น **สรุปข้อมูล** และเพิ่มปุ่ม **Export Excel**
เปิดจาก `จัดการกิจกรรม → รายชื่อ`

ไฟล์ที่ได้มี **ชีตเดียวชื่อ Summary** หัวเรื่องคือ
`สรุปจำนวนข้อมูลพนักงานลงทะเบียน (ชื่อกิจกรรม)` และหัวคอลัมน์กลางตารางคือชื่อกิจกรรม
เปลี่ยนชื่อกิจกรรมแล้วไฟล์เปลี่ยนตามเอง

```
Location | Section | Manpower | <ชื่อกิจกรรม>                            | Remark
                     number     Completed | Not Complete | Completion Rate
```

ตัวเลขเป็นตัวเลขจริง คอลัมน์ % เป็นรูปแบบเปอร์เซ็นต์ มีแถว Total รายสาขา
และ Grand Total ท้ายสุด

## หน้าที่เอาออก

| หน้า | เหตุผล |
| --- | --- |
| สรุปการลงทะเบียน (`/admin/reports`) | ซ้ำกับสรุปข้อมูลในหน้ารายชื่อของกิจกรรม |
| คำแปลหลายภาษา (`/admin/translations`) | ไม่ได้ใช้ |
| สิ่งที่ต้องทำ ฝั่งพนักงาน (`/surveys`) | ใช้คู่กับหน้าสรุปการลงทะเบียนที่เอาออกไปแล้ว |

**การแปลอัตโนมัติยังทำงานอยู่ตามปกติ** เอาออกเฉพาะหน้าจัดการคำแปลเท่านั้น
ตัวแปลเบื้องหลังยังแปลเนื้อหาที่ผู้ดูแลกรอกเป็นอังกฤษและญี่ปุ่นให้เหมือนเดิม

ตารางและ API ของแบบสำรวจยังอยู่ครบในฐานข้อมูล ไม่ได้ลบทิ้ง
ถ้าวันหนึ่งอยากเปิดใช้อีกก็ต่อหน้าจอกลับเข้าไปได้ โดยข้อมูลเดิมไม่หาย

## ตำแหน่ง แผนก และสาขา

- เพิ่มแผนก **ER** เข้าในรายการ (รวมเป็น 31 แผนก)
- **สาขา** เปลี่ยนเป็นช่องเลือก **PD / TS / BKK** พร้อมตัวเลือก อื่นๆ
- หน้า **เพิ่มผู้ดูแลระบบ** แผนกเลือกจาก **HR / HRD / HRM / GA / ER**
  ส่วนตำแหน่งใช้รายการเดียวกับพนักงาน
  (แยกรายการแผนกเพราะผู้ดูแลระบบส่วนใหญ่มาจากงานบุคคลและธุรการ ไม่ใช่แผนกผลิต)
- ตัวเลือกท้ายรายการเปลี่ยนคำเป็น **อื่นๆ** และช่องพิมพ์เองขึ้นคำว่า **โปรดระบุ**

## สิทธิ์

- **ลบพนักงาน** เห็นปุ่มและกดได้เฉพาะ role `admin` บัญชีอื่นไม่เห็นปุ่มเลย
  เซิร์ฟเวอร์กันไว้อีกชั้นที่ `RequireAdmin`
- **ปรับคะแนน** เฉพาะ `admin` หรือตำแหน่ง **Chief Engineer ขึ้นไป** (ตามเดิม)
  ช่องตำแหน่งในหน้าเพิ่มผู้ดูแลระบบมีข้อความกำกับไว้ เพราะตำแหน่งที่เลือก
  ตัดสินว่าบัญชีนั้นปรับคะแนนได้หรือไม่

## คะแนนพิเศษฝั่งพนักงาน

แสดงไอคอน K-Point พร้อมตัวเลขทุกที่ และ **แสดงเสมอแม้ยอดเป็นศูนย์**
เพื่อให้พนักงานรู้ว่ามีคะแนนแบบนี้อยู่ และเข้าใจว่าของรางวัลที่ติดไอคอนนี้
ต้องใช้คะแนนกระเป๋าไหนแลก

เห็นได้ที่หน้าแรก (ยอดคงเหลือ การ์ดของรางวัล การ์ดกิจกรรม) หน้าคะแนน
(ยอดคงเหลือและประวัติรายการ) และหน้าของรางวัล (ยอดคงเหลือ ราคา และหน้ารายละเอียด)

## ปุ่มรับทราบประกาศ

ตัดช่อง *บังคับให้กดรับทราบ* กับคำอธิบายยาวออกจากฟอร์ม เหลือเป็นคำอธิบายสั้น ๆ
ว่าปุ่มทำงานอย่างไร พฤติกรรมเป็นแบบนี้เสมอ

- **ประกาศสั้น** แสดงเนื้อหาครบหน้าจอ → กดรับทราบได้ทันที
- **ประกาศยาว** ต้องเลื่อนจนสุดเนื้อหา → ปุ่มรับทราบจึงกดได้

## ช่องเลือกทุกช่องใช้สไตล์เดียวกัน

เดิมหลายช่องยังเป็น `<select>` ของเบราว์เซอร์ ซึ่ง **จัดสไตล์รายการตัวเลือกไม่ได้**
เพราะเบราว์เซอร์วาดเอง หน้าตาจึงหลุดจากส่วนอื่นของระบบและต่างกันไปในแต่ละเครื่อง

เพิ่มคอมโพเนนต์ `Select` ใน `components/ComboBox.jsx` ที่ใช้โครงเดียวกับช่องเลือก
ตำแหน่งงาน แล้วเปลี่ยนช่องเลือกทั้งหมดในฟอร์มมาใช้ตัวนี้ — ระดับสมาชิก สถานะ
ชนิดกิจกรรม ชนิดคะแนน ระดับขั้นต่ำ สีการ์ดระดับ หมวดแจ้งเตือน ช่องทางส่ง
และช่องกรองในตาราง

`ComboBox` รับตัวเลือกได้สองแบบ

```js
options={['Member', 'Silver', 'Elite']}                       // ค่ากับคำที่แสดงเหมือนกัน
options={[{ value: 'vote', label: 'โหวต (ได้คะแนนทันที)' }]}  // เก็บค่าอังกฤษ แสดงคำไทย
```

ช่องค้นหาจะโผล่เองเมื่อมีตัวเลือกเกินแปดรายการ รายการสั้นกดแล้วเห็นครบอยู่แล้ว
ไม่ต้องมีช่องค้นหาให้รก

## ไฟล์ Excel ใช้สีตามไฟล์ตัวอย่าง

| ส่วน | สี |
| --- | --- |
| หัวตาราง | เทอร์ควอยซ์ `#33CCCC` ตัวหนังสือดำหนา กรอบดำ |
| แถวที่ยังทำไม่ครบ | เหลือง `#FFFF00` |
| แถวรวมของสาขา | ฟ้าอ่อน `#DCE6F1` |
| แถวรวมทั้งหมด | เทอร์ควอยซ์เหมือนหัวตาราง |
| หัวเรื่อง | แดง `#C00000` |

คอลัมน์ Completion Rate ใช้ **แถบข้อมูล (data bar)** สีเขียวแทนการเติมสีพื้นทั้งช่อง
ความยาวแถบจึงบอกสัดส่วนได้เหมือนไฟล์ตัวอย่าง ตรึงช่วงไว้ที่ 0 ถึง 1 เสมอ
ไม่ให้ Excel คิดสเกลเองจากค่าต่ำสุด-สูงสุดในคอลัมน์ ไม่งั้นแผนกที่ทำได้ 20%
จะมีแถบยาวเต็มช่องถ้าบังเอิญเป็นค่าสูงสุดในชีตนั้น

แถว Grand Total แยกเป็นสองบรรทัดตามไฟล์ตัวอย่าง บรรทัดบนเป็นจำนวนคน
บรรทัดล่างเป็นสัดส่วน (Manpower = 100% เสมอ)

หัวเรื่องไม่ผสานเซลล์แล้ว ปล่อยให้ข้อความล้นไปทางขวาได้
เพราะถ้าผสาน ชื่อกิจกรรมยาว ๆ จะถูกตัดหายไปตั้งแต่เปิดไฟล์

## อื่น ๆ

- **คะแนนพิเศษในการ์ดคะแนน** เอาแถบพื้นหลังสีเทาออก เปลี่ยนเป็นบรรทัดเดียว
  คั่นด้วยเส้นบาง ๆ บนพื้นการ์ดเดิม — กล่องสีอ่อนบนการ์ดสีเข้มกลายเป็นแถบเทา
  ที่แย่งสายตาไปจากคะแนนหลัก
- **คำโปรย** ของประกาศข่าวสารเอาออกแล้ว ทั้งในฟอร์มและหน้าที่พนักงานเห็น
  การ์ดในหน้าจัดการแสดงเนื้อหาสองบรรทัดแรกแทน

## คะแนนพิเศษมีวันหมดอายุ

คะแนนพิเศษเป็นรางวัลเฉพาะกิจ จึงควรมีอายุ ไม่ใช่สะสมค้างไว้ตลอดไป
กำหนดวันหมดอายุได้สองที่

- **ปรับคะแนนพนักงาน** เลือกคะแนนพิเศษแล้วจะมีช่อง *คะแนนพิเศษหมดอายุวันที่* โผล่มา
- **สร้าง/แก้ไขกิจกรรม** ช่องวันหมดอายุจะโผล่เมื่อกรอกคะแนนพิเศษมากกว่า 0
  กิจกรรมที่ไม่ให้คะแนนพิเศษจะไม่มีช่องนี้มารกฟอร์ม

เว้นว่างไว้ = ไม่มีวันหมดอายุ

### เก็บวันหมดอายุค่าเดียวต่อคน และเลื่อนออกไปเสมอ

ระบบเก็บวันหมดอายุไว้ที่ผู้ใช้ **ค่าเดียว** ไม่ได้แยกรายก้อน
เมื่อได้คะแนนพิเศษก้อนใหม่ ระบบจะเก็บ **วันที่ไกลกว่า** ไว้

ตัวอย่าง: มี 100 คะแนนหมดอายุ 31 ธ.ค. แล้วได้อีก 50 คะแนนหมดอายุ 15 พ.ย.
ผลคือ 150 คะแนน หมดอายุ 31 ธ.ค. — พนักงานไม่ควรเสียคะแนนก้อนใหม่
เพียงเพราะก้อนเก่าใกล้หมดอายุ

ถ้าต้องการให้แต่ละก้อนหมดอายุแยกกันจริง ๆ ต้องทำเป็นบัญชีรายก้อน (lot)
ซึ่งซับซ้อนกว่ามากและยังไม่ได้ทำ

### การตัดยอดทำสองทาง

| ทาง | เมื่อไหร่ | ทำไม |
| --- | --- | --- |
| ตอนพนักงานเปิดแอป | ทันที | ยอดที่เห็นตรงกับความจริงเสมอ ไม่ต้องรอรอบ |
| ตัวตั้งเวลา | ทุกชั่วโมง | รายงานฝั่งผู้ดูแลถูกต้องแม้พนักงานไม่ได้เปิดแอป |

ตัดยอดแล้วบันทึกรายการเดินบัญชีไว้เป็นยอดติดลบชื่อ *คะแนนพิเศษหมดอายุ*
พนักงานจึงย้อนดูได้ว่าคะแนนหายไปเพราะหมดอายุ ไม่ใช่ระบบคำนวณผิด

หน้าของรางวัลและการกดแลกก็ตัดยอดก่อนทุกครั้ง กันกรณีเห็นว่าแลกไหว

## ไฟล์ Excel ใช้ฟอนต์และรูปแบบตรงกับไฟล์ตัวอย่าง

เปิดไฟล์ `แบบฟอร์มลงทะเบียน Line OA` อ่านค่ารูปแบบของทุกเซลล์ออกมาแล้วคัดลอกมาใช้

| สิ่งที่ปรับ | ค่าที่ใช้ |
| --- | --- |
| ฟอนต์ทั้งไฟล์ | **Angsana New ขนาด 16** |
| หัวเรื่องแถว 3 | ตัวหนาสีดำ (เดิมเป็นสีแดง) |
| ข้อความกำกับจำนวนพนักงาน | ขีดเส้นใต้ |
| ช่องชื่อสาขา | พื้นเทาอ่อน `#F2F2F2` ตัวหนา จัดกึ่งกลางทั้งแนวตั้งและแนวนอน |
| เส้นคั่นระหว่างแถวข้อมูล | **เส้นประ** ส่วนเส้นแนวตั้งเป็นเส้นทึบ |
| แถวรวมทั้งหมด | กรอบหนา (medium) |
| แถบ Completion Rate | สีทึบ `#66FF99` ไม่ไล่เฉด · ช่วงแบบ min/max |
| ความสูงแถว | แถว 4 สูง 6 (แถวคั่นบาง) · แถว 5–6 สูง 18 |

เส้นประระหว่างแถวข้อมูลคือจุดที่ต่างจากของเดิมมากที่สุดเมื่อดูด้วยตา
ตารางยาว ๆ อ่านง่ายกว่าเส้นทึบทั้งหมด

### ข้อควรรู้เรื่องแถบ Completion Rate

ช่วงของแถบใช้ **min/max** ให้ตรงกับไฟล์ตัวอย่าง คือ Excel คิดสเกลเองจากค่าต่ำสุด
และสูงสุดที่มีอยู่จริงในคอลัมน์ ไม่ได้เทียบกับ 100%

ผลคือ **แถบเทียบกันเองภายในไฟล์** ถ้าทุกแผนกอยู่ระหว่าง 33% ถึง 59%
แถบของ 33% จะสั้นที่สุดและของ 59% จะยาวเต็มช่อง ทั้งที่ไม่มีแผนกไหนทำได้ครบเลย

เวลาอ่านรายงานให้ดู **ตัวเลขเปอร์เซ็นต์ที่เขียนกำกับไว้เป็นหลัก**
ส่วนแถบใช้เทียบว่าแผนกไหนตามหลังแผนกไหน

ถ้าอยากให้แถบเทียบกับ 100% เสมอ เปลี่ยนที่ `frontend/src/lib/xlsxReport.js`
จาก `<cfvo type="min"/><cfvo type="max"/>` เป็น
`<cfvo type="num" val="0"/><cfvo type="num" val="1"/>`


## สีในไฟล์ Excel (อ่านค่ามาจากไฟล์ตัวอย่างโดยตรง)

| ส่วน | สีพื้น | สีตัวหนังสือ |
| --- | --- | --- |
| หัวตาราง | `#33CCCC` | ดำ ตัวหนา |
| ช่องชื่อสาขา | `#F2F2F2` | ดำ ตัวหนา |
| แถวที่ยังทำไม่ครบ (คอลัมน์ Section ถึง Not Complete) | `#FFFF00` | ดำ |
| แถวรวมของสาขา | `#DCE6F1` | ดำ ตัวหนา |
| แถวรวมทั้งหมด — Manpower | `#33CCCC` | ดำ ตัวหนา |
| แถวรวมทั้งหมด — Completed | `#33CCCC` | **เหลือง `#FFFF00`** |
| แถวรวมทั้งหมด — Not Complete | `#33CCCC` | **ชมพู `#FF7979`** |
| แถบ Completion Rate | `#66FF99` ทึบ · ช่วง min/max | — |

สองจุดที่สังเกตยากแต่ต่างจริง

- **คอลัมน์ Completion Rate และ Remark ไม่ถูกเติมสีเหลือง** แม้แถวนั้นจะยังทำไม่ครบ
  สีเหลืองหยุดที่คอลัมน์ Not Complete เพราะช่อง Rate มีแถบสีเขียวทับอยู่แล้ว
- **ช่อง Remark ของแถวรวมสาขาเป็นพื้นขาว** ไม่ใช่ฟ้าอ่อนเหมือนช่องอื่นในแถวเดียวกัน


## คอลัมน์ที่เป็นสูตร ไม่ใช่ตัวเลขตายตัว

ไฟล์ที่ดาวน์โหลดใส่สูตรของ Excel ไว้เหมือนไฟล์ตัวอย่าง แก้ตัวเลขในไฟล์แล้วยอดอัปเดตตามทันที

| ช่อง | สูตร |
| --- | --- |
| Not Complete (แถวข้อมูล) | `=C7-D7` |
| Completion Rate (แถวข้อมูล) | `=IF(C7=0,0,D7/C7)` |
| Manpower / Completed (แถว Total) | `=SUM(C7:C9)` |
| Not Complete (แถว Total) | `=C10-D10` |
| Manpower / Completed (Grand Total) | `=C10+C12+C14` |

**Grand Total บวกเฉพาะแถว Total ของแต่ละสาขา** ไม่ได้ใช้ `SUM` ครอบทั้งตาราง
เพราะแถว Total อยู่ปนกับแถวข้อมูล ถ้าครอบทั้งหมดจะนับซ้ำเป็นสองเท่า

สองเรื่องที่ตั้งใจทำ

- **ครอบด้วย `IF(...=0,0,...)`** แทนการหารตรง ๆ แผนกที่ไม่มีพนักงานจะได้ไม่ขึ้น `#DIV/0!`
  ซึ่งทำให้ยอดรวมทั้งคอลัมน์พังตามไปด้วย
- **เก็บค่าที่คำนวณไว้แล้วคู่กับสูตรเสมอ** โปรแกรมที่เปิดไฟล์แต่ไม่คำนวณสูตรเอง
  (เช่น Google Sheets ตอนนำเข้า หรือตัวอ่านไฟล์ในระบบอื่น) จะเห็นตัวเลขถูกต้องทันที
  แทนที่จะเห็นช่องว่าง

# ส่วนที่เพิ่มรอบที่แปด

## ลงทะเบียนหน้างานแล้วได้คะแนนทันที (ตรวจตำแหน่ง)

ในฟอร์มสร้าง/แก้ไขกิจกรรมมีกล่อง **พื้นที่จัดงาน** ให้ใส่ละติจูด ลองจิจูด และรัศมี
มีปุ่ม *ใช้ตำแหน่งปัจจุบัน* ให้กดกรอกพิกัดจากที่ผู้ดูแลยืนอยู่ได้เลย

**ตั้งพิกัดไว้** → พนักงานลงทะเบียนได้เฉพาะตอนอยู่ในพื้นที่ และ **ได้คะแนนทันทีที่ลงทะเบียน**
ระบบบันทึกเป็น `attended` ให้เลย ไม่ต้องให้แอดมินมาสแกนเช็คอินซ้ำอีกรอบ

**เว้นพิกัดว่างไว้** → ลงทะเบียนจากที่ไหนก็ได้แล้วค่อยเช็คอินหน้างานตามเดิม
กิจกรรมเก่าทั้งหมดจึงทำงานเหมือนเดิมโดยไม่ต้องแก้อะไร

### ข้อความผิดพลาดแยกตามสาเหตุ

แยกเป็นสามแบบเพราะทางแก้ของผู้ใช้ต่างกันสิ้นเชิง
ถ้าขึ้นข้อความเดียวกันหมดผู้ใช้จะไม่รู้ว่าต้องทำอะไรต่อ

| สาเหตุ | สิ่งที่ผู้ใช้ต้องทำ |
| --- | --- |
| ไม่อนุญาตให้ใช้ตำแหน่ง | เปิดสิทธิ์ตำแหน่งในตั้งค่าเบราว์เซอร์ |
| หาตำแหน่งไม่ได้ / หมดเวลา | เปิด GPS หรือเดินออกไปที่โล่ง |
| อยู่นอกพื้นที่ | เดินเข้าไปใกล้จุดจัดงาน — **ระบบบอกระยะห่างให้ด้วย** |

การ์ดกิจกรรมฝั่งพนักงานติดป้าย *ต้องลงทะเบียนที่หน้างาน* ไว้ตั้งแต่หน้ารายการ
พนักงานจะได้ไม่กดจากที่บ้านแล้วเจอข้อความปฏิเสธโดยไม่รู้สาเหตุ

### สองเรื่องที่ควรรู้

**เผื่อความคลาดเคลื่อนของ GPS อีก 50 เมตร** จากรัศมีที่ตั้งไว้
GPS ในอาคารเพี้ยนได้หลายสิบเมตร ถ้าไม่เผื่อ คนที่ยืนอยู่ในงานจริงจะถูกปฏิเสธ
แล้วต้องไปตามแอดมินให้แก้ให้ ซึ่งเสียเวลาทั้งสองฝ่ายมากกว่าการปล่อยคนขอบ ๆ ผ่าน

**พิกัดมาจากเครื่องของผู้ใช้ จึงปลอมได้ถ้าตั้งใจจริง**
ตัวนี้กันกรณีที่เกิดบ่อยคือ "ลืมมางาน แล้วกดลงทะเบียนจากที่บ้าน"
แต่กันคนที่ใช้เครื่องมือปลอมพิกัดไม่ได้ ถ้าต้องการความแน่นอนกว่านี้
ให้ใช้การเช็คอินด้วย QR ที่หน้างานควบคู่ไปด้วย

ระบบบันทึกพิกัดตอนลงทะเบียนไว้ในตาราง `event_registrations` ตรวจย้อนหลังได้

## ประกาศข่าวสารแนบลิงก์และไฟล์ PDF

ฟอร์มประกาศมีกล่อง **ลิงก์และไฟล์แนบ** เพิ่มมา

- **ลิงก์** ใส่ URL กับข้อความบนปุ่มได้ เช่นลิงก์ไป Google Form พร้อมปุ่ม *ทำแบบสำรวจ*
- **ไฟล์แนบ** อัปโหลด PDF ได้ ขนาดไม่เกิน 15 MB พนักงานกดเปิดอ่านได้จากหน้าประกาศ

ทั้งสองปุ่มเปิดแท็บใหม่เสมอ กดแล้วจะได้ไม่หลุดจากประกาศที่ยังกดรับทราบไม่เสร็จ

เซิร์ฟเวอร์ตรวจว่าเป็น PDF จริงจากไบต์ในไฟล์ (`%PDF-`) ไม่เชื่อนามสกุลหรือ
`accept` ของช่องเลือกไฟล์ เพราะสองอย่างนั้นปลอมได้ง่าย และไฟล์ที่ผู้ใช้เปิด
ในเบราว์เซอร์เป็นช่องทางโจมตีที่ดีถ้าปล่อยผ่าน ชื่อไฟล์บนดิสก์เป็นตัวอักษรสุ่ม
ส่วนชื่อเดิมเก็บไว้แค่แสดงผล

# Deploy บน cloud (ไม่ต้องให้ผู้ใช้กดผ่านคำเตือน)

ปัญหา "ผู้ใช้ต้องกดผ่านหน้าคำเตือนความปลอดภัย" เกิดจากใบรับรองแบบ self-signed
ที่ใช้ในวงแลน ซึ่งเบราว์เซอร์ไม่เชื่อถือ แก้ได้ด้วยการใช้ **ชื่อโดเมนจริง + ใบรับรอง
จาก Let's Encrypt** ซึ่งเบราว์เซอร์ทุกตัวเชื่อถืออยู่แล้ว

ไฟล์ `docker-compose.cloud.yml` กับ `Caddyfile` ทำให้อัตโนมัติทั้งหมด

## สามขั้นตอน

1. ชี้ A record ของโดเมนมาที่ IP ของเครื่อง เช่น `rewards.example.com`
2. เปิดพอร์ต 80 และ 443 ที่ firewall หรือ security group
   (พอร์ต 80 ใช้ตอนยืนยันความเป็นเจ้าของโดเมน ปิดไม่ได้)
3. ใส่สองบรรทัดนี้ใน `rewards.env`

```
SITE_DOMAIN=rewards.example.com
ACME_EMAIL=it@example.com
```

แล้วสั่ง

```bash
docker compose -f docker-compose.cloud.yml up -d --build
```

Caddy จะขอใบรับรองให้เองตอนเริ่มทำงาน และต่ออายุให้ตลอดโดยไม่ต้องสั่งอะไรอีก
ผู้ใช้เข้าที่ `https://rewards.example.com` ได้เลย ไม่มีเลขพอร์ต ไม่มีคำเตือน

ใบรับรองถูกเก็บไว้ใน volume `caddy-data` รีสตาร์ทเครื่องแล้วไม่ต้องขอใหม่
ซึ่งสำคัญเพราะ Let's Encrypt จำกัดจำนวนครั้งที่ขอต่อสัปดาห์

## ยังเหลืออีกหนึ่งอย่างที่ตัดไม่ได้

**กล่องขอสิทธิ์ตำแหน่ง** ที่เบราว์เซอร์เด้งถามว่า "อนุญาตให้เว็บนี้ใช้ตำแหน่งของคุณไหม"
**ตัดออกไม่ได้** ไม่ว่าจะทำอะไรก็ตาม เป็นข้อกำหนดด้านความเป็นส่วนตัวของเบราว์เซอร์
ที่เว็บไซต์ปิดเองไม่ได้โดยตั้งใจ

แต่ผู้ใช้กดครั้งเดียวต่อหนึ่งโดเมน แล้วเบราว์เซอร์จำไว้ตลอด ไม่ถามซ้ำอีก
ตราบใดที่ยังเป็นโดเมนเดิม — อีกเหตุผลที่ควรใช้โดเมนจริงแทนการเข้าด้วย IP
เพราะถ้า IP เปลี่ยน ผู้ใช้ต้องกดอนุญาตใหม่ทุกคน

## ถ้าใช้ load balancer หรือ Cloudflare อยู่แล้ว

ถ้ามีตัวจัดการ TLS อยู่ข้างหน้าแล้ว ให้ใช้ `docker-compose.prod.yml` ตามเดิม
แล้วชี้ตัวนั้นมาที่พอร์ต 4008 แทน ไม่ต้องใช้ Caddy ซ้ำ

**ข้อควรระวัง:** ตัวจัดการ TLS ข้างหน้าต้องคุยกับ backend แบบ https ด้วย
หรือไม่ก็ส่ง header `X-Forwarded-Proto: https` มา ถ้าหลุดเป็น http
เบราว์เซอร์จะยังมองว่าไม่ปลอดภัยและปิดการระบุตำแหน่งเหมือนเดิม

เลือกช่อง *ผู้ดูแลระบบ* ที่หน้าเข้าสู่ระบบได้เลย ไม่ต้องสร้างบัญชีแยกอีกใบ
และยังใช้ฝั่งพนักงานได้ตามปกติ (สะสมคะแนน แลกของรางวัล ลงทะเบียนกิจกรรม)

สิ่งที่ทำไม่ได้คือกลุ่มเมนู **ตั้งค่าระบบ** — บัญชีผู้ดูแลระบบ, Audit Logs,
System Settings รวมถึงการลบพนักงานและการล้างคะแนนประจำปี ซึ่งย้อนกลับไม่ได้

## ใครปรับคะแนนได้

ต้องผ่าน **ทั้งสองเงื่อนไขพร้อมกัน**

| เงื่อนไข | ค่าที่ผ่าน |
| --- | --- |
| แผนก | GA · ER · HR · HRM · HRD |
| ตำแหน่ง | Co-General Manager · Assistant General Manager · Co-Manager · Manager · Assistant Manager · Chief Officer |

ผู้จัดการฝ่ายผลิตจึงปรับคะแนนไม่ได้ แม้ตำแหน่งจะชื่อ Manager เหมือนกัน
ส่วน role `admin` ทำได้ทุกอย่างเสมอโดยไม่ดูแผนกหรือตำแหน่ง

รายการนี้**ไม่ได้เรียงตามลำดับชั้น** แต่เป็นรายชื่อที่ระบุมาเฉพาะเจาะจง
จึงเทียบแบบ "อยู่ในรายการหรือไม่" ไม่ใช่ "สูงกว่าตำแหน่งนี้หรือไม่"
Director กับ Chief Engineer ไม่อยู่ในรายการ จึงปรับคะแนนไม่ได้

## ตารางสิทธิ์ (ทดสอบจริงแล้ว)

| บัญชี | จัดการพนักงาน | ตั้งค่าระบบ | ปรับคะแนน | ลบพนักงาน |
| --- | :---: | :---: | :---: | :---: |
| role `admin` | ✓ | ✓ | ✓ | ✓ |
| HR / Manager | ✓ | ✗ | ✓ | ✗ |
| HR / Officer | ✓ | ✗ | ✗ | ✗ |
| PDF / Manager | ✗ | ✗ | ✗ | ✗ |

PDF / Manager เข้าช่องผู้ดูแลระบบไม่ได้เลยตั้งแต่หน้าเข้าสู่ระบบ

## โครงสร้างโค้ด

รายการแผนก ตำแหน่ง และกติกาสิทธิ์อยู่ที่ **`backend/org/org.go`**
แยกเป็นแพ็กเกจของตัวเองเพราะทั้ง `middleware` และ `controllers` ต้องใช้
ถ้าปล่อยไว้ใน `controllers` แล้วให้ `middleware` เรียก จะเกิดการอ้างวนกัน

หน้าเว็บมีสำเนาที่ `frontend/src/lib/org.js` — **แก้ที่ไหนต้องแก้ให้ตรงกันทั้งสองที่**

การกันสิทธิ์ทำสองชั้นที่เซิร์ฟเวอร์

| middleware | ใครผ่าน |
| --- | --- |
| `RequireOffice` | admin, ga, พนักงานแผนกหลังบ้าน |
| `RequireAdmin` | admin เท่านั้น — ใช้กับกลุ่มตั้งค่าระบบ |

แผนกและตำแหน่งถูก**อ่านจากฐานข้อมูลทุกครั้ง** ไม่ได้ฝังไว้ใน token
ย้ายคนออกจากแผนกหรือลดตำแหน่งแล้วสิทธิ์หายทันที ไม่ต้องรอ token หมดอายุอีกเจ็ดวัน

การซ่อนเมนูที่หน้าจอเป็นแค่ความสุภาพกับสายตา ของจริงกันที่เซิร์ฟเวอร์ทั้งหมด

# แก้บั๊ก: เพิ่มพนักงานโดยไม่ใส่อีเมลแล้วขึ้น "เซิร์ฟเวอร์มีปัญหา"

อาการใน log ของเซิร์ฟเวอร์

```
pq: null value in column "email" of relation "users" violates not-null constraint
```

## สาเหตุ

ฐานข้อมูลถูกสร้างจาก `schema.sql` รุ่นเก่าที่ตั้ง `users.email` เป็น **NOT NULL**
แต่ฟอร์มเพิ่มพนักงานไม่ได้บังคับกรอกอีเมล (ไม่มีเครื่องหมาย \*)
พอเว้นว่าง ระบบส่ง NULL ลงไปแล้วฐานข้อมูลปฏิเสธ

`schema.sql` ฉบับปัจจุบันตั้งเป็นเว้นว่างได้อยู่แล้ว แต่ฐานข้อมูลที่ใช้งานอยู่
ไม่ได้ถูกสร้างใหม่ จึงยังค้างเงื่อนไขเดิมไว้

## ทางแก้

ไฟล์ `db/migrations/006_optional_user_columns.sql` ปลดเงื่อนไข NOT NULL
ของคอลัมน์ที่ไม่บังคับกรอก ได้แก่ `email`, `birth_date`, `avatar_url`,
`points_expire_at`, `terms_accepted_at` ให้ตรงกับ `schema.sql` ฉบับปัจจุบัน

**แค่ปิดแล้วเปิดเซิร์ฟเวอร์ใหม่** (`go run .`) migration จะทำงานเอง
ไม่ต้องสั่ง SQL เองและไม่กระทบข้อมูลเดิม

ไฟล์นี้ยังเปลี่ยนอีเมลที่เป็นค่าว่างให้เป็น NULL ด้วย เพราะคอลัมน์อีเมลห้ามซ้ำ
ถ้าปล่อยเป็นค่าว่างไว้ จะเพิ่มพนักงานที่ไม่มีอีเมลได้แค่คนเดียว
ส่วน NULL นั้น PostgreSQL ไม่ถือว่าซ้ำกัน

## ปรับปรุงเพิ่ม: ข้อความผิดพลาดบอกสาเหตุ

เดิมข้อผิดพลาดของฐานข้อมูลทุกชนิดถูกกลบด้วย "เซิร์ฟเวอร์มีปัญหา กรุณาลองใหม่อีกครั้ง"
ซึ่งไม่ช่วยอะไรเลยและทำให้ไล่หาสาเหตุยาก

ตอนนี้ `web.Fail` แปลข้อผิดพลาดที่รู้สาเหตุแล้วให้อ่านรู้เรื่อง

| รหัส | ความหมาย | ข้อความที่แสดง |
| --- | --- | --- |
| 23502 | คอลัมน์ห้ามเว้นว่าง | บอกชื่อช่องที่มีปัญหา และบอกให้เปิดเซิร์ฟเวอร์ใหม่เพื่อให้ migration ทำงาน |
| 23514 | ค่าไม่อยู่ในรายการที่ยอมรับ | บอกว่าค่าที่กรอกไม่ถูกต้อง |

ที่เหลือยังใช้ข้อความกลาง ๆ ตามเดิม เพราะไม่ควรเปิดเผยรายละเอียดภายในให้ผู้ใช้เห็น

# แก้บั๊ก: พนักงานแผนก GAG เข้าหน้าผู้ดูแลระบบไม่ได้

## สาเหตุ

รหัสแผนกสองชุดไม่ตรงกัน

| ที่ | รหัสที่ใช้ |
| --- | --- |
| ทะเบียนพนักงาน (ช่องเลือกแผนก) | **GAG** · HRM · HRD · ER |
| รายการแผนกหลังบ้านที่กำหนดไว้ | **GA** · HR · HRM · HRD · ER |

ฝ่ายธุรการในทะเบียนพนักงานใช้รหัส **GAG** แต่รายการแผนกหลังบ้านเขียนว่า **GA**
พนักงานที่เลือก GAG จากช่องเลือกจึงไม่มีทางตรงกับรายการเลย และถูกปฏิเสธทุกครั้ง
เช่นเดียวกับ HR ที่ไม่มีอยู่ในช่องเลือกแผนกตั้งแต่แรก

## ทางแก้

รับทั้งสองแบบที่ใช้เรียกกันจริง

```
BackOfficeSections = GA · GAG · ER · HR · HRM · HRD
```

- **GA กับ GAG** คือฝ่ายธุรการเหมือนกัน
- **HR กับ HRM / HRD** คือฝ่ายบุคคลเหมือนกัน

และเพิ่ม GA กับ HR เข้าไปในช่องเลือกแผนกของหน้าจัดการพนักงานด้วย (รวมเป็น 33 รายการ)
ไม่งั้นพนักงานสองแผนกนี้ต้องกด "อื่นๆ" แล้วพิมพ์เอง ซึ่งพิมพ์ผิดเมื่อไหร่
สิทธิ์เข้าหลังบ้านก็หายทันทีโดยไม่มีใครรู้สาเหตุ

การเทียบรหัสแผนกไม่สนตัวพิมพ์เล็กใหญ่และช่องว่างหัวท้ายอยู่แล้ว
ข้อมูลที่นำเข้าจากไฟล์ Excel มักมีช่องว่างติดมา

# เพิ่มพนักงาน: บังคับกรอกตำแหน่ง แผนก และสาขา

ช่องที่มีเครื่องหมาย `*` ตอนนี้คือ

```
รหัสพนักงาน *   รหัสผ่าน *   ชื่อ - สกุล *
ตำแหน่ง *       แผนก *       สาขา *
```

อีเมล เบอร์โทรศัพท์ และวันเกิด ยังเว้นว่างได้ตามเดิม

สามช่องที่เพิ่มมาไม่ใช่แค่ข้อมูลประกอบ แต่ถูกใช้จริงสองทาง

- **ตำแหน่งกับแผนก** ตัดสินสิทธิ์เข้าหลังบ้านและสิทธิ์ปรับคะแนน
- **แผนกกับสาขา** เป็นคอลัมน์ Section และ Location ในรายงานสรุป
  ปล่อยว่างไว้แล้วพนักงานคนนั้นจะไปรวมอยู่ในแถว `-` ของรายงาน

ตรวจทั้งที่หน้าเว็บและที่เซิร์ฟเวอร์ ช่องทั้งสามใช้ ComboBox ที่เป็นปุ่มกับรายการ
ไม่ใช่ `<input>` ของเบราว์เซอร์ จึงใส่ `required` ให้เบราว์เซอร์ช่วยตรวจไม่ได้
ต้องตรวจเองตอนกดบันทึก และเซิร์ฟเวอร์ตรวจซ้ำเพราะการเรียก API ตรงไม่ได้ผ่านฟอร์ม

# แก้บั๊ก: พนักงานแผนกหลังบ้านล็อกอินแล้วได้หน้าขาวเปล่า

## สาเหตุ — เด้งวนไม่จบ

เส้นทาง `/admin` ถูกตั้งเป็น `RequireAuth admin` (เฉพาะผู้ดูแลระบบตัวจริง)
แต่ตัวเปลี่ยนเส้นทางสั่งว่า "ถ้าเข้าหลังบ้านได้ ให้ส่งไป `/admin`"

พนักงานแผนกหลังบ้านจึงเข้า `/admin` → ถูกปฏิเสธ → ส่งไป `/admin` → ถูกปฏิเสธ
วนแบบนี้ไม่จบ React Router เลยไม่วาดอะไรเลย ได้หน้าขาวที่ไม่มีข้อความบอกสาเหตุ

เป็นอาการที่ไล่หายากเพราะไม่มี error ขึ้นทั้งใน console และใน log ของเซิร์ฟเวอร์
API ฝั่งหลังบ้านปล่อยผ่านหมดแล้ว ติดแค่ที่การจัดเส้นทางของหน้าเว็บอย่างเดียว

## ทางแก้

**หนึ่ง** เปลี่ยนหน้าหลังบ้านทั้งหมดเป็น `RequireAuth staff` ให้ตรงกับฝั่งเซิร์ฟเวอร์
ที่เปลี่ยนเป็น `RequireOffice` ไปแล้ว จุดที่พลาดคือแก้ฝั่งเซิร์ฟเวอร์แล้วลืมแก้ฝั่งหน้าเว็บ

**สอง** กันการเด้งวนไว้ที่ตัวเปลี่ยนเส้นทาง ถ้าปลายทางคือหน้าเดิมที่เพิ่งถูกปฏิเสธ
ให้ออกไปฝั่งพนักงานแทน ต่อให้มีใครตั้งสิทธิ์ผิดอีกในอนาคต
ผู้ใช้ก็จะไปโผล่ที่หน้าที่ใช้งานได้ ไม่ใช่เจอหน้าขาว

**สาม** เส้นทาง `/admin/settings/:key` ใช้ร่วมกันสองกลุ่ม

| key | ใครเข้าได้ |
| --- | --- |
| `membership` | เมนู "จัดการสมาชิก" — พนักงานแผนกหลังบ้านใช้ได้ |
| `accounts` · `audit` · `system` | กลุ่ม "ตั้งค่าระบบ" — ผู้ดูแลระบบตัวจริงเท่านั้น |

จึงย้ายการกันสิทธิ์ไปไว้ที่ระดับหน้าแทนระดับเส้นทาง และ**แสดงข้อความบอกเหตุผล
แทนการเด้งกลับเงียบ ๆ** เพราะการเด้งเงียบทำให้ผู้ใช้ไม่รู้ว่าเกิดอะไรขึ้น

## ผลหลังแก้ (ทดสอบด้วยบัญชี GAG / Chief Officer)

เปิดได้ทุกหน้า: ภาพรวม · จัดการพนักงาน · จัดการของรางวัล · จัดการกิจกรรม ·
จัดการคะแนน · จัดการสมาชิก · ประกาศข่าวสาร · Notifications · Banner / FAQ / Terms

ถูกปฏิเสธ (403) ตามที่ควร: Admin Accounts · Audit Logs · System Settings

# แก้บั๊ก: กด "จัดการสมาชิก" แล้วหน้าค้าง

## สาเหตุ

หน้า `pages/admin/Settings.jsx` เรียกใช้ `useAuth()` แต่**ไม่มีบรรทัด import**

```js
const { user } = useAuth();   // ใช้อยู่
// ไม่มี: import { useAuth } from '../../context/AuthContext';
```

ตอนเพิ่มการกันสิทธิ์รอบก่อน ผมแก้โค้ดในไฟล์แต่บรรทัด import ไม่ได้ถูกเพิ่มเข้าไป

**การ build ผ่านฉลุย** เพราะ Vite กับ Rollup มองว่าชื่อที่หาไม่เจอ
อาจเป็นตัวแปรระดับ global ที่มีอยู่ตอนรันจริง จึงไม่ฟ้องอะไรเลย
แล้วไปพังตอนผู้ใช้กดเข้าหน้านั้น ได้หน้าขาวที่ไม่มีข้อความบอกสาเหตุ

## ทางแก้ และการกันไม่ให้เกิดซ้ำ

นอกจากเพิ่ม import ที่ขาดแล้ว เพิ่มสคริปต์ `frontend/scripts/check-imports.mjs`
ที่ไล่หา hook ซึ่งถูกเรียกใช้โดยไม่ได้ import ทั่วทั้ง `src`

```bash
npm run check     # ตรวจอย่างเดียว
npm run build     # ตรวจก่อนเสมอ ไม่ผ่านจะไม่ build ต่อ
```

ผูกไว้กับ `build` เลย เพื่อให้ไฟล์ที่มีปัญหาแบบนี้ไม่มีทางหลุดขึ้น server ได้

ไม่ได้เพิ่มไลบรารีใหม่ เป็นสคริปต์ Node ธรรมดาไฟล์เดียว
ทดสอบแล้วว่าจับเคสนี้ได้จริง (ลบบรรทัด import ออกแล้วสคริปต์ฟ้องและหยุด build)

# แก้บั๊ก: กดปุ่มปิดในหน้าต่าง "ใครอ่านแล้ว" แล้วหน้าขาว

## สาเหตุ

ตอนกดปิด `announcement` กลายเป็น `null` ทันที แต่ `data` ยังค้างของเดิมอยู่
เพราะ `useEffect` ที่ล้าง `data` ทำงาน **หลัง** การวาดรอบนั้นจบไปแล้ว

โค้ดจึงอ่าน `announcement.title` จากค่า `null` → React ถอดทั้งหน้าทิ้ง → หน้าขาว

แก้โดยหยุดวาดทันทีเมื่อไม่มีประกาศ (`if (!announcement) return null`)
ไล่ตรวจหน้าต่างอื่นทั้งหมดแล้ว ที่เหลือมีการ์ด `{active && ...}` กันไว้อยู่แล้ว

## กันไม่ให้เกิดซ้ำ — ErrorBoundary

เพิ่ม `components/ErrorBoundary.jsx` ครอบทั้งแอป คอมโพเนนต์ไหนพังระหว่างวาด
ผู้ใช้จะเห็นข้อความบอกพร้อมปุ่ม "โหลดหน้าใหม่" กับ "กลับหน้าแรก"
และมีรายละเอียดข้อผิดพลาดให้คัดลอกส่งต่อได้ แทนที่จะเจอหน้าขาวที่ไม่บอกอะไรเลย

# ลงทะเบียนในแอปแล้วได้คะแนนทันที

เดิมกิจกรรมทั่วไปต้องรอให้ผู้ดูแลสแกนเช็คอินหน้างานก่อนจึงได้คะแนน
พนักงานจึงเห็นสถานะ **"รอเช็คอิน"** ค้างอยู่ และต้องต่อแถวให้สแกนอีกรอบ
ทั้งที่กดลงทะเบียนในแอปตอนอยู่หน้างานไปแล้ว

ตอนนี้ **การลงทะเบียนคือการยืนยันว่ามาถึงงานแล้ว จ่ายคะแนนเลยทุกกรณี**

| กิจกรรม | ตอนลงทะเบียน |
| --- | --- |
| ตั้งพิกัดพื้นที่จัดงานไว้ | ตรวจตำแหน่งก่อน ผ่านแล้วได้คะแนนทันที |
| ไม่ได้ตั้งพิกัด | ได้คะแนนทันที ลงทะเบียนจากที่ไหนก็ได้ |

ป้ายสถานะในใบรายชื่อเปลี่ยนจาก *เช็คอินแล้ว / รอเช็คอิน*
เป็น **ลงทะเบียนแล้ว ได้คะแนนแล้ว / ยังไม่ได้รับคะแนน**
(แถวที่ยังเป็นอย่างหลังคือข้อมูลเก่าก่อนเปลี่ยนกติกา)

## เช็คอิน มีไว้สำหรับคนที่ไม่ได้ลงทะเบียนมาจากแอป

ปุ่ม **เช็คอิน** และหน้าต่าง **เช็คอินกิจกรรม** ใช้งานได้เหมือนเดิมทุกอย่าง
ทั้งการสแกนรหัสพนักงานที่ลงทะเบียนไว้แล้ว และการเช็คอินแบบหน้างาน
(walk-in) สำหรับคนที่ยังไม่ได้ลงทะเบียน

สแกนรหัสพนักงานแล้วระบบแยกสามกรณีให้เอง

| กรณี | สิ่งที่เกิดขึ้น |
| --- | --- |
| **ยังไม่ได้ลงทะเบียน** | คืนชื่อมาให้ตรวจก่อน กดยืนยันแล้วจึงบันทึกและให้คะแนน |
| **ลงทะเบียนในแอปแล้ว** | ขึ้นกล่องแจ้ง *"(ชื่อ) ลงทะเบียนในแอปแล้ว"* **ไม่จ่ายคะแนนซ้ำ** |
| **พิมพ์รหัสผิด** | แจ้งว่าไม่พบพนักงานรหัสนี้ |

กรณีที่สองตอบกลับเป็น *สถานะ* ไม่ใช่ error เพราะเป็นเรื่องที่เกิดได้ปกติหน้างาน
พนักงานอาจไม่แน่ใจว่าลงทะเบียนไปหรือยังเลยมาต่อแถวให้สแกนอีกรอบ
ผู้ดูแลควรเห็นข้อความอธิบายในหน้าต่างเดิม ไม่ใช่กล่อง error สีแดงที่ดูเหมือนระบบพัง

# ปรับถ้อยคำและหน้าตา

- ป้ายสถานะในใบรายชื่อเหลือ **ลงทะเบียนแล้ว** คำเดียว
- หน้าต่างเช็คอินตัดคำอธิบายใต้หัวข้อออก
- กล่องแจ้งคนที่ลงทะเบียนแล้วเหลือบรรทัดเดียว **(ชื่อ) ลงทะเบียนในแอปแล้ว**
- ช่อง *ข้อความบนปุ่ม* ของลิงก์ในประกาศ ตัด placeholder ออก
- เอาปุ่ม **ใครอ่านแล้ว** กับหน้าต่างรายชื่อออกจากหน้าประกาศข่าวสาร
  แถบความคืบหน้าบนการ์ดยังอยู่ ยังเห็นว่ามีคนกดรับทราบแล้วกี่คนจากทั้งหมดกี่คน

## ป็อปอัปประกาศ จัดกลางจอทุกขนาด

เดิมบนมือถือเป็นแผ่นเลื่อนขึ้นจากขอบล่าง ซึ่งเหมาะกับเมนูหรือตัวเลือกสั้น ๆ
แต่ประกาศมีทั้งแบบสั้นและแบบยาว **ประกาศสั้นจะไปกองอยู่ติดขอบล่างจอ**
เหลือพื้นที่ว่างโล่งข้างบน ดูเหมือนป็อปอัปโฆษณามากกว่าประกาศทางการ

จัดกลางแล้วประกาศสั้นลอยอยู่กลางจอเหมือนป้ายประกาศ
ส่วนประกาศยาวยังขยายเต็มความสูงที่กำหนดไว้เหมือนเดิม จึงได้ทั้งสองแบบ

**ข้อแลกเปลี่ยนที่ควรรู้:** ปุ่มรับทราบจะขยับสูงขึ้นจากขอบล่างเล็กน้อย
เอื้อมนิ้วโป้งไกลกว่าเดิมนิดหน่อยบนมือถือจอใหญ่ แต่ปุ่มนี้กดครั้งเดียวจบ
ไม่ใช่ปุ่มที่ต้องกดซ้ำ ๆ จึงแลกกับหน้าตาที่ดูเป็นทางการกว่าได้

# แจ้งปัญหาตำแหน่งเป็นหน้าต่างกลางจอ

เดิมใช้แถบแจ้งเตือนมุมจอ ซึ่ง **หายไปเองในไม่กี่วินาที**
ผู้ใช้ที่กดลงทะเบียนแล้วมองไปทางอื่นจะไม่เห็นเลยว่าทำไมไม่สำเร็จ
แล้วกดซ้ำไปเรื่อย ๆ โดยไม่รู้สาเหตุ

ตอนนี้เป็นหน้าต่างกลางจอ มีวงกลมไอคอนหมุดขนาดใหญ่
อ่านออกตั้งแต่ยังไม่ทันอ่านตัวหนังสือว่าเป็นเรื่องตำแหน่ง
ไม่ใช่เรื่องคะแนนหรือสิทธิ์

แต่ละสาเหตุมีหัวข้อ คำอธิบาย คำแนะนำ และสีของตัวเอง

| สาเหตุ | หัวข้อ | คำแนะนำ | ปุ่มลองอีกครั้ง |
| --- | --- | --- | :---: |
| อยู่นอกพื้นที่ | คุณไม่ได้อยู่ในพื้นที่จัดงาน (บอกระยะห่าง) | เข้ามาในบริเวณงานก่อน | ✓ |
| ไม่อนุญาต | ยังไม่ได้อนุญาตให้ใช้ตำแหน่ง | แตะไอคอนแม่กุญแจข้างแถบที่อยู่ | ✓ |
| หาไม่เจอ | หาตำแหน่งของคุณไม่ได้ | เปิด GPS หรือเดินออกไปที่โล่ง | ✓ |
| ไม่ใช่ https | ระบบยังเปิดผ่าน https ไม่ได้ | — | ✗ |

สามกรณีแรกผู้ใช้แก้เองได้จึงมีปุ่ม **ลองอีกครั้ง** ที่กดแล้วลงทะเบียนต่อได้เลย
ไม่ต้องปิดหน้าต่างแล้วหากิจกรรมใหม่ ส่วนกรณีสุดท้ายต้องให้ผู้ดูแลแก้ที่เซิร์ฟเวอร์

เงื่อนไขนี้ก็กลายเป็นจริงทุกครั้ง ข้อความจึงขึ้นว่าโหวตทั้งที่ผู้ใช้กดลงทะเบียน

แก้โดยเลือกจาก `res.kind` ซึ่งเป็นชนิดของกิจกรรมจริง ๆ
ทดสอบแล้วทั้ง 6 กิจกรรมในชุดข้อมูลทดสอบขึ้นข้อความถูกต้องตามชนิด

# หน้าต่างยืนยันผลลัพธ์

เปลี่ยนจากแถบแจ้งเตือนมุมจอเป็นหน้าต่างกลางจอที่ **ปิดตัวเองใน 3 วินาที**
กดปิดเองก่อนได้ เพราะคะแนนที่ได้รับเป็นผลลัพธ์หลักของการกดปุ่ม
ควรเห็นชัดว่าได้เท่าไหร่ ไม่ใช่แวบผ่านไปที่มุมจอ

หน้าตาประกอบด้วย

- วงกลมเครื่องหมายถูกสีเขียวขนาดใหญ่
- หัวข้อ **ลงทะเบียนเรียบร้อยแล้ว** หรือ **โหวตเรียบร้อยแล้ว** ตามชนิดกิจกรรม
- คะแนนที่ได้ ตัวใหญ่กว่าหัวข้อเพราะเป็นพระเอกของหน้าต่างนี้
- คะแนนพิเศษพร้อมไอคอน K-Point ถ้ากิจกรรมนั้นให้ด้วย

ตัวจับเวลาถูกเคลียร์ทิ้งทุกครั้งที่หน้าต่างปิด ไม่งั้นผู้ใช้ที่กดปิดเอง
แล้วลงทะเบียนกิจกรรมถัดไปทันที จะโดนตัวจับเวลาของรอบก่อนปิดหน้าต่างใหม่ทิ้งกลางคัน

# ปรับหน้าภาพรวม (Dashboard)

## กิจกรรมที่ได้รับความสนใจสูงสุด — เปอร์เซ็นต์เทียบกันได้แล้ว

เดิมหารด้วย `capacity` ของแต่ละกิจกรรม ซึ่งผู้ดูแลตั้งไว้ไม่เท่ากัน
บางงานตั้ง 500 บางงานไม่ตั้งเลย (0 = ไม่จำกัด แล้วนับเป็น 100%)

ผลคือกิจกรรมที่มีคนเข้าร่วม **เท่ากันคือ 4 คน** แสดง `0.8%` กับ `100%` อยู่ข้างกัน
และความยาวแถบก็ไม่ตรงกับตัวเลข เพราะแถบเทียบกับกิจกรรมอันดับหนึ่ง
ส่วนตัวเลขหารด้วย capacity — คนละตัวหารกันคนละทาง

เปลี่ยนมาใช้ **จำนวนพนักงานทั้งหมด** เป็นตัวหารเดียวกันทุกแถว

```
1. 9.9 Compliance Day        1 จาก 6 คน  = 16.67%   (แถบยาว 17%)
2. โหวตทริปท่องเที่ยวประจำปี   1 จาก 6 คน  = 16.67%   (แถบยาว 17%)
```

ตัวเลขกับแถบตรงกันแล้ว และเทียบระหว่างกิจกรรมได้จริง

## อัตราการมีส่วนร่วมตามแผนก — เลื่อนดูได้

แสดงสี่แผนกแรกในกรอบที่เห็น ที่เหลือเลื่อนดูในกล่องเดียวกัน

โรงงานมีสามสิบกว่าแผนก ถ้าปล่อยยาวทั้งหมดการ์ดใบนี้จะสูงกว่าการ์ดข้าง ๆ
หลายเท่าแล้วหน้าจอทั้งหน้าเสียสมดุล ความสูงตั้งไว้พอดีสี่แถว
ผู้ใช้จึงเห็นว่ายังมีต่ออีกข้างล่าง ไม่ใช่คิดว่ามีแค่นี้

## การเคลื่อนไหวของคะแนน — ระยะห่างของเดือน

แก้สองจุด

**หนึ่ง** เดิมคืนเฉพาะเดือนที่มีรายการ เดือนที่ว่างหายไปจากกราฟเลย
แท่งสองเดือนที่ห่างกันครึ่งปีจึงวางติดกัน ทำให้อ่านแนวโน้มผิด
ตอนนี้ใช้ `generate_series` สร้างทุกเดือนในช่วงมาก่อนแล้วค่อยต่อข้อมูลจริง
เดือนที่ไม่มีรายการได้ค่า 0 และยังกินพื้นที่บนแกนเวลาตามจริง

**สอง** จำกัดความกว้างของช่องแต่ละเดือนไว้ที่ 72px แล้วจัดกลุ่มไว้กลางกราฟ
ถ้าหารความกว้างทั้งหมดด้วยจำนวนเดือนตรง ๆ ช่วงที่มีไม่กี่เดือน
แท่งจะถูกดันห่างกันจนดูเหมือนข้อมูลกระจายทั่วทั้งปี

# ปรับกราฟในหน้าภาพรวม (รอบที่สอง)

## การเคลื่อนไหวของคะแนน — เลื่อนดูแนวนอน

เดิมยืดกราฟให้พอดีกรอบเสมอ ช่วงสั้นแท่งจะอ้วนและห่างกันมาก
ส่วนช่วงยาวแท่งจะผอมจนดูไม่ออก

ตอนนี้ **แต่ละเดือนกินที่เท่ากันเสมอ 72px** กราฟจึงกว้างขึ้นตามช่วงที่เลือก
แล้วเลื่อนดูในแนวนอนเอา แท่งของทุกเดือนขนาดเท่ากันหมด เทียบด้วยตาได้ตรง ๆ
(ช่วง 12 เดือน = กราฟกว้าง 936px เลื่อนดูได้)

เพิ่มเติมให้ตรงกับกราฟตัวอย่าง

- เส้นแกนตั้งและแกนนอนเป็นเส้นทึบ มีกรอบอ่านง่ายขึ้น
- ขีดสั้น ๆ ที่แกนตั้งตรงระดับตัวเลข ช่วยกวาดตาจากตัวเลขไปหาเส้นได้ไม่หลง
- เส้นคะแนนคงเหลือสะสมเปลี่ยนจากเส้นประสีเข้ม เป็นเส้นทึบสีหลักพร้อมจุดทุกเดือน
- เพิ่ม **คะแนนคงเหลือสะสม** เข้าไปในคำอธิบายสีมุมขวาบน ซึ่งเดิมไม่มี
  ทั้งที่เส้นนี้วาดอยู่บนกราฟมาตลอด

## แนวโน้มอัตราการเข้าร่วม — 100% ตลอดเพราะสูตรใช้ไม่ได้แล้ว

เดิมคิดจาก **เช็คอินแล้ว หารด้วย ลงทะเบียนทั้งหมด**

สูตรนี้เคยใช้ได้ตอนที่ลงทะเบียนแล้วต้องรอเช็คอินอีกขั้น แต่พอเปลี่ยนให้
ลงทะเบียนแล้วได้คะแนนทันที ทุกแถวจึงถูกบันทึกเป็น attended หมด
ตัวหารกับตัวตั้งเท่ากันเสมอ ค่าที่ได้เลยเป็น 100% ตลอด ซึ่งไม่ได้บอกอะไรเลย

เปลี่ยนมาคิดจาก **เฉลี่ยแต่ละกิจกรรมมีคนเข้าร่วมกี่เปอร์เซ็นต์ของพนักงานทั้งหมด**

```
2026-11   4 กิจกรรม · เฉลี่ยมาร่วม 0.5 คน  =  8.3%
2026-12   4 กิจกรรม · เฉลี่ยมาร่วม 1.0 คน  = 16.7%
```

เดือนไหนจัดสามงานแล้วมีคนมางานละราว ๆ หนึ่งในสี่ขององค์กร ก็จะได้ประมาณ 25%
อ่านแล้วรู้ทันทีว่าเดือนนั้นกิจกรรมดึงคนได้ดีแค่ไหน และเทียบข้ามเดือนได้จริง

เติมเดือนที่ไม่มีกิจกรรมให้ครบช่วงด้วย เส้นกราฟจะได้ไม่เหลือจุดเดียวลอย ๆ
และเขียนกำกับใต้กราฟว่าตัวเลขคิดมาจากอะไร

# กราฟหน้าภาพรวม ทำตามแบบที่ออกแบบไว้

## เดือนที่ไม่มีข้อมูล เว้นว่างไว้

เดิมเดือนที่ไม่มีรายการจะถูกวาดเป็นแท่งศูนย์หรือจุดที่ระดับศูนย์
ซึ่งอ่านผิดความหมาย — "ไม่ได้จัดกิจกรรมเลย" กับ "จัดแล้วไม่มีคนมา"
เป็นคนละเรื่องกันโดยสิ้นเชิง

ตอนนี้ฝั่งเซิร์ฟเวอร์ส่งธง `has_data` มาด้วย เดือนที่เป็นเท็จจะ

- **ไม่วาดแท่ง** ในกราฟคะแนน
- **ไม่วาดจุด และเส้นขาดตรงนั้น** ในกราฟแนวโน้ม ไม่ลากข้ามไปเอง

แต่เดือนนั้นยังกินพื้นที่บนแกนเวลาตามจริง ระยะห่างระหว่างเดือนจึงถูกต้อง

## แถบเลื่อน

กราฟที่กว้างกว่ากรอบมีแถบเลื่อนทรงแคปซูลอยู่ใต้กราฟ **เห็นได้ตลอดเวลา**
ไม่ใช่แถบจาง ๆ ที่โผล่เฉพาะตอนเลื่อนเมาส์ผ่าน ไม่งั้นผู้ใช้จะไม่รู้ว่ายังมีข้อมูลต่อ

ถ้าข้อมูลพอดีกรอบอยู่แล้ว รางจะหายไป จะได้ไม่หลอกตาว่ายังมีต่อ
(ตรวจด้วย `ResizeObserver` ทุกครั้งที่ขนาดกรอบเปลี่ยน)

## รายละเอียดอื่นที่ปรับให้ตรงแบบ

| ส่วน | เดิม | ใหม่ |
| --- | --- | --- |
| แกนตั้ง / แกนนอน | เส้นจาง | เส้นทึบเข้ม พร้อมขีดบอกระดับ |
| ระดับบนแกน | 5 ขีด (0/25/50/75/100) | 6 ขีด (0/20/40/60/80/100) |
| หน่วยเปอร์เซ็นต์ | `100%` | `100 %` เว้นวรรคตามแบบ |
| แท่งคะแนนที่แจก | `#00ADB0` | `#1FC2A0` |
| แท่งคะแนนที่ใช้ | `#3B82F6` | `#3B6DF5` |
| เส้นยอดสะสม | เส้นประสีเข้ม | เส้นทึบสีหลัก พร้อมจุดทุกเดือน |
| หัวข้อการ์ด | ข้อความอย่างเดียว | มีไอคอน ⓘ ชี้ค้างแล้วอธิบายที่มาของตัวเลข |

ไอคอน ⓘ ใช้ `title` ของปุ่ม เบราว์เซอร์แสดงคำอธิบายให้เอง
ไม่ต้องเขียน tooltip เพิ่มและใช้ได้กับโปรแกรมอ่านหน้าจอด้วย

# แก้กราฟคะแนน: เส้นต้องอยู่เหนือแท่ง และแกนต้องไม่เลื่อนหาย

## ปัญหาที่หนึ่ง — แกนตั้งเลื่อนหายไปพร้อมกราฟ

ตอนทำให้กราฟเลื่อนแนวนอนได้ แกนตั้งถูกวาดอยู่ใน SVG เดียวกับพื้นกราฟ
พอเลื่อนไปดูเดือนหลัง ตัวเลขบนแกนเลื่อนออกนอกจอไปด้วย
เหลือแต่แท่งลอย ๆ ที่อ่านไม่ออกว่าสูงเท่าไหร่

แยกเป็นสองส่วนที่วางชิดกัน

| ส่วน | อยู่ไหน |
| --- | --- |
| แกนตั้ง + ตัวเลข + ขีดบอกระดับ | นอกกรอบเลื่อน ติดอยู่กับที่เสมอ |
| เส้นตาราง แท่ง เส้นยอดสะสม ชื่อเดือน | ในกรอบเลื่อน เลื่อนดูได้ |

## ปัญหาที่สอง — เส้นยอดสะสมไปอยู่ใต้แท่ง

มีสองสาเหตุซ้อนกัน

**หนึ่ง แท่งกับเส้นใช้คนละสเกล** แต่ละอย่างมีเพดานของตัวเอง
ตำแหน่งของเส้นเทียบกับแท่งจึงไม่มีความหมายเลย
แก้โดยใช้แกนเดียวกัน เพดานคิดจากค่าสูงสุดของทั้งสองอย่างแล้วเผื่ออีก 15%
และปัดขึ้นเป็นตัวเลขกลม ๆ (`niceMax`) ตัวเลขบนแกนจะได้ไม่เป็นเศษอย่าง 8,137

**สอง เส้นยอดสะสมเริ่มนับจากศูนย์** ทุกครั้งที่เปลี่ยนช่วงเวลา
ยอดสะสมของเดือนแรกจึงเท่ากับ "แจกลบใช้" ของเดือนนั้นเดือนเดียว
ซึ่งย่อมน้อยกว่าคะแนนที่แจกทั้งเดือนเสมอ เส้นเลยจมอยู่ใต้แท่ง

แก้โดยให้ฝั่งเซิร์ฟเวอร์ส่ง `balance` มาด้วย ซึ่งเริ่มนับจาก
**คะแนนที่ค้างอยู่ในระบบก่อนเข้าช่วงที่เลือก** ไม่ใช่ศูนย์
ตรงกับความหมายของคำว่า "คะแนนคงเหลือสะสม" จริง ๆ และเส้นจะลอยเหนือแท่งเองตามธรรมชาติ

ทดสอบกับข้อมูลจริงแล้ว ทุกเดือนที่มีข้อมูลเส้นอยู่เหนือแท่ง

```
2026-10  แจก 8,100  ใช้ 0  ยอดสะสม  8,100   เส้นเหนือแท่ง
2026-11  แจก 3,730  ใช้ 0  ยอดสะสม 11,830   เส้นเหนือแท่ง
```

# เกลากราฟให้ตรงกับแบบ

เทียบกับภาพออกแบบทีละจุด แล้วแก้ตามนี้

| ส่วน | เดิม | ตามแบบ |
| --- | --- | --- |
| เส้นตารางแนวนอน | มีเส้นจางพาดทั้งกราฟ | **ไม่มี** ปล่อยพื้นโล่ง ใช้ขีดที่แกนแทน |
| ขีดบนแกน | ขีดเดียวตรงตัวเลข | ขีดยาวตรงตัวเลข + **ขีดสั้นคั่นกลาง** |
| มุมแท่ง | มนทั้งสี่มุม | **มนเฉพาะมุมบน** ฐานติดเส้นแกน |
| ความกว้างแท่ง | 16 | 18 ชิดกันขึ้น (ช่องไฟ 3) |
| ตัวเลขบนแกน | `20K` | `20 K` เว้นวรรคหน้าหน่วย |
| เส้นแกน | บาง 1.5 | หนา 2 เข้มขึ้น |

## รายละเอียดสองอย่างที่ต้องเขียนเอง

**แท่งมนเฉพาะมุมบน** ใช้ `rx` ของ `<rect>` ไม่ได้ เพราะมนทั้งสี่มุม
แท่งเตี้ย ๆ จะกลายเป็นแคปซูลลอยไม่ติดเส้นแกน จึงวาดเป็น `<path>` เอง
และบีบรัศมีตามความสูงของแท่ง แท่งที่สูงแค่ 3px ก็ยังเป็นสี่เหลี่ยมปลายมน ไม่บวม

**ตัวเลขบนแกน** เขียนตัวย่อใหม่ให้เว้นวรรคหน้าหน่วยและตัดทศนิยมที่ลงตัว

```
เพดาน 500,000  ->  0   100 K   200 K   300 K   400 K   500 K
เพดาน  20,000  ->  0     4 K     8 K    12 K    16 K    20 K
เพดาน   1,200  ->  0     240     480     720     960   1.2 K
```

## หัวการ์ดไม่ตัดคำกลางคัน

คำอธิบายสีสามอันเคยถูกบีบจนคำว่า "คะแนนที่แจก" ขึ้นบรรทัดใหม่กลางคำ
ใส่ `whitespace-nowrap` ให้แต่ละอัน และให้ทั้งก้อนตกลงบรรทัดใหม่พร้อมกัน
เมื่อการ์ดแคบ ดีกว่าหักคำทีละอัน

ซ่อนปุ่มลูกศรหัวท้ายรางเลื่อนด้วย บางเบราว์เซอร์ใส่มาให้เองแล้วรางดูรกกว่าแบบ

| แนวโน้มอัตราการเข้าร่วม | เดือน · อัตราการเข้าร่วม |

> **หมายเหตุ** ในคำสั่งที่ได้รับ ข้อมูลของสองกราฟสลับกันอยู่
> (ให้กราฟอัตราการเข้าร่วมแสดงคะแนนที่แจก และให้กราฟคะแนนแสดงอัตราการเข้าร่วม)
> ตารางข้างบนจับคู่ตามข้อมูลที่แต่ละกราฟมีจริง เพราะกราฟอัตราการเข้าร่วม
> ไม่มีตัวเลขคะแนนอยู่ในนั้นเลย และกราฟคะแนนก็ไม่มีอัตราการเข้าร่วม

## รายละเอียดที่ดูแลไว้

**แถบรับเมาส์เต็มความสูงของคอลัมน์** ชี้ตรงไหนของเดือนนั้นก็ติด
ไม่ต้องเล็งให้โดนแท่งหรือจุดเล็ก ๆ ซึ่งบางเดือนเตี้ยมากจนแทบจิ้มไม่โดน
และบนจอสัมผัสแทบเป็นไปไม่ได้ คอลัมน์ที่ชี้อยู่จะมีพื้นจาง ๆ บอกด้วย

**วาดกล่องเป็น SVG ไม่ใช่ div ลอยด้านบน** เพราะกราฟเลื่อนแนวนอนได้
ถ้าใช้ div จะต้องคำนวณตำแหน่งใหม่ทุกครั้งที่เลื่อนแล้วมักหลุดตำแหน่ง
วาดใน SVG เดียวกันแล้วกล่องเลื่อนไปพร้อมกราฟเอง

**กล่องไม่ล้นขอบ** ถ้าเดือนที่ชี้อยู่ริมซ้ายหรือริมขวา กล่องจะขยับเข้ามาเอง
ไม่โผล่ออกนอกพื้นกราฟจนอ่านไม่ครบ

**เดือนที่ไม่มีข้อมูล** ชี้แล้วยังขึ้นกล่อง แต่บอกว่า *ไม่มีรายการในเดือนนี้*
หรือ *ไม่มีกิจกรรม* แทนตัวเลข ผู้ใช้จะได้รู้ว่าระบบไม่ได้ค้าง

## คำอธิบายสีอยู่บรรทัดเดียว

ใส่ `whitespace-nowrap` ให้แต่ละอัน ชื่ออย่าง "คะแนนที่แจก" จึงไม่ถูกหัก
เป็น "คะแนนที่ / แจก" กลางคำอีก ภาษาไทยไม่มีช่องว่างระหว่างคำ
เบราว์เซอร์จึงตัดบรรทัดเองตามพจนานุกรม ต้องสั่งห้ามเป็นรายจุด

# เส้นในกราฟคะแนน คือคะแนนที่เคลื่อนไหวรวม

**เส้น = คะแนนที่แจก + คะแนนที่ใช้** ของเดือนนั้น ใช้แกนเดียวกับแท่ง

เลือกค่านี้เพราะต้องการเส้นที่บอกว่า *เดือนนี้คึกคักขึ้นหรือซบลงกว่าเดือนก่อน*
ยอดคงเหลือสะสมทำหน้าที่นั้นไม่ได้ เพราะมันขึ้นอย่างเดียวตามเวลา
เดือนที่เงียบก็ยังเห็นเส้นสูงขึ้นเรื่อย ๆ อ่านแนวโน้มไม่ออก

อีกข้อดีคือผลรวมย่อมมากกว่าหรือเท่ากับแท่งที่สูงที่สุดเสมอ
เส้นจึงลอยเหนือแท่งเองตามธรรมชาติ ตรงกับแบบที่ออกแบบไว้
โดยไม่ต้องเอาตัวเลขจากนอกช่วงเวลามาดันให้สูง

```
ม.ค.   แจก 80,000  ใช้ 50,000  เคลื่อนไหวรวม 130,000   —
ก.พ.   แจก 62,000  ใช้ 38,000  เคลื่อนไหวรวม 100,000   ต่ำลง
มี.ค.  แจก 78,000  ใช้ 55,000  เคลื่อนไหวรวม 133,000   สูงขึ้น
เม.ย.  แจก 52,000  ใช้ 30,000  เคลื่อนไหวรวม  82,000   ต่ำลง
```

เดือนที่ไม่มีรายการเว้นเส้นขาดตรงนั้น ไม่ลากข้ามไปเอง

## เส้นถูกยกขึ้นจากยอดแท่งเล็กน้อย

เดือนที่ยังไม่มีใครใช้คะแนน ผลรวมจะเท่ากับคะแนนที่แจกพอดี
เส้นกับยอดแท่งจึงทับกันสนิทจนดูเหมือนเส้นหายไป

ยกเส้นขึ้น 9 พิกเซล และใส่ขอบขาวหนา 5 พิกเซลไว้ใต้เส้นหลัก
ช่วงที่เส้นเฉียดยอดแท่งจึงยังแยกออกจากกันได้ด้วยตา

```
ก่อนแก้   ยอดแท่ง y=57.5   เส้น y=57.5   ห่างกัน 0 px
หลังแก้   ยอดแท่ง y=57.5   เส้น y=48.5   ห่างกัน 9 px
```

**เป็นการขยับเพื่อการมองเห็นเท่านั้น ไม่ได้แก้ตัวเลข**
ตำแหน่งเส้นจึงสูงกว่าค่าจริงบนแกนอยู่เล็กน้อย (ราว 9 พิกเซล)
ถ้าต้องการตัวเลขที่แม่นยำให้เอาเมาส์ชี้ กล่องที่ขึ้นมาแสดงค่าจริงเสมอ

เส้นถูกกันไม่ให้ล้นขอบบนด้วย เดือนที่ค่าชนเพดานแกนพอดีจึงยังอยู่ในกรอบ

## คำอธิบายในไอคอน เหลือแค่สูตร

| กราฟ | ข้อความ |
| --- | --- |
| การเคลื่อนไหวของคะแนน | `เส้น = คะแนนที่แจก + คะแนนที่ใช้` |
| แนวโน้มอัตราการเข้าร่วม | `อัตรา = ผู้เข้าร่วมเฉลี่ยต่อกิจกรรม ÷ พนักงานทั้งหมด` |

# กราฟยืดหยุ่นตามขนาดตัวเลขแค่ไหน

เพดานแกนไม่ได้ตั้งตายตัว คำนวณใหม่ทุกครั้งจากข้อมูลจริงในช่วงที่เลือก
แล้วปัดขึ้นเป็นตัวเลขกลม ๆ (`niceMax`) ทดสอบแล้วรองรับตั้งแต่หลักหน่วยถึงหลักพันล้าน

```
ยอดแจก          เพดานแกน        ตัวเลขบนแกน
         1               5       0  1  2  3  4  5
     3,000           4,000       0  800  1.6 K  2.4 K  3.2 K  4 K
    30,000          40,000       0  8 K  16 K  24 K  32 K  40 K
   250,000         300,000       0  60 K  120 K  180 K  240 K  300 K
 3,500,000       5,000,000       0  1 M  2 M  3 M  4 M  5 M
 1,200,000,000   1,500,000,000   0  300 M  600 M  900 M  1.2 B  1.5 B
```

วันที่แจก 30,000 แกนจะขยับเป็น 40,000 เอง แท่งไม่ล้นกรอบและไม่เตี้ยติดพื้น

## สองจุดที่แก้เพิ่มจากการทดสอบนี้

**หลักพันล้านเคยขึ้นว่า `1500 M`** ซึ่งยาวและอ่านยาก เพิ่มหน่วย `B` เข้าไป
กลายเป็น `1.5 B` ตัวเลขยาวสุดเหลือ 5 ตัวอักษร แกนกว้าง 62px จึงยังพอทุกช่วง

**ค่าน้อยมากเคยได้ตัวเลขซ้ำกัน** ยอดแจก 1 คะแนนจะได้เพดาน 1.5
แล้วขีดทั้งหกถูกปัดเป็น `0 0 1 1 1 2` ซึ่งอ่านไม่รู้เรื่อง
ตั้งเพดานขั้นต่ำไว้ที่ 5 เพราะแกนแบ่งเป็น 5 ช่วง ทุกขีดจึงเป็นจำนวนเต็มที่ต่างกันเสมอ

## ข้อจำกัดที่ยังมี

แกนเป็นสเกลเชิงเส้น ถ้าเดือนหนึ่งแจก 30,000 แต่เดือนอื่นแจกหลักร้อย
แท่งของเดือนเล็ก ๆ จะเตี้ยจนแทบมองไม่เห็น เป็นธรรมชาติของกราฟแท่งทั่วไป
เอาเมาส์ชี้ยังอ่านตัวเลขจริงได้ หรือจะเลือกช่วงเวลาให้แคบลงเพื่อดูเฉพาะเดือนที่สนใจ

# แบบประเมินความพึงพอใจหลังกิจกรรม

## ตั้งค่าได้ที่ System Settings

| ค่า | ค่าเริ่มต้น | ความหมาย |
| --- | --- | --- |
| `event.feedbackLeadHours` | 1 | แบบประเมินขึ้นก่อนกิจกรรมจบกี่ชั่วโมง |
| `event.feedbackOpenDays` | 7 | เปิดให้ตอบต่อได้อีกกี่วันหลังจบกิจกรรม |

เวลาจบกิจกรรมคิดจาก **วันสุดท้ายของงานบวกเวลาเลิก** กิจกรรมหลายวันจึงใช้วันสุดท้าย

## ป็อปอัปฝั่งพนักงาน

ขึ้นให้เฉพาะ **คนที่ลงทะเบียนกิจกรรมนั้นจริง** และยังไม่เคยตอบ
มีห้าคำถามแบบห้าระดับ (มากที่สุด ถึง น้อยที่สุด) กับช่องข้อเสนอแนะที่ไม่บังคับ

ตั้งใจให้ **ปิดทิ้งได้** ไม่บังคับเหมือนประกาศข่าวสาร
เพราะแบบประเมินที่บังคับตอบจะได้คำตอบที่กดผ่าน ๆ ซึ่งแย่กว่าไม่มีข้อมูลเลย
ปิดไปแล้วยังกลับมาตอบได้จนกว่าจะหมดเวลาที่ตั้งไว้

ถ้ามีทั้งประกาศข่าวสารและแบบประเมินพร้อมกัน ประกาศจะอยู่ชั้นบนกว่า
พนักงานจะได้อ่านเรื่องที่บังคับก่อน

## ผลที่ผู้ดูแลเห็น

อยู่ในหน้าต่าง **สรุปข้อมูล** ของกิจกรรมนั้น แสดงค่าเฉลี่ยรายข้อพร้อมแถบสี
(เขียวตั้งแต่ 4 ขึ้นไป ทองตั้งแต่ 3 แดงต่ำกว่านั้น) และรายการข้อเสนอแนะ

**ไม่ส่งชื่อผู้ตอบออกจากเซิร์ฟเวอร์เลย** เพราะความเห็นเรื่องคุณภาพงาน
จะตรงไปตรงมาก็ต่อเมื่อคนตอบมั่นใจว่าไม่ถูกตามไปถาม
และบอกพนักงานไว้บนหน้าจอก่อนกดส่งด้วย

# หน้าผลประเมินกิจกรรม (Feedback)

เมนูหลักต่อจาก **จัดการสมาชิก** เปิดให้ผู้ดูแลระบบและฝ่ายธุรการ

| ส่วน | เนื้อหา |
| --- | --- |
| ตัวกรอง | เลือกกิจกรรม และเลือกปี พ.ศ. 2565–2700 |
| สรุปด้านบน | ผู้ตอบทั้งหมด · กิจกรรมที่มีผลประเมิน · คะแนนเฉลี่ยรวม |
| คะแนนเฉลี่ย (รายข้อ) | ห้าข้อพร้อมแถบสี เทียบกับเต็ม 5 เสมอ |
| คะแนนเฉลี่ย (รายเดือน) | **กราฟแท่ง** เพดานตรึงที่ 5 |
| รายกิจกรรม | ตารางคะแนนรายข้อ เรียงจากคะแนนสูงสุดลงมา |
| ข้อเสนอแนะ | ความเห็นทั้งหมด ไม่มีชื่อผู้เขียน |

## ตัวกรอง

**เลือกกิจกรรม** รายการมาจากกิจกรรมที่ **มีผลประเมินจริงในปีนั้น**
ไม่ใช่รายการกิจกรรมทั้งหมด กิจกรรมที่ยังไม่มีใครประเมินจึงไม่โผล่มาให้เลือกแล้วเจอหน้าว่าง

รายการตัวเลือกไม่ถูกกรองตามกิจกรรมที่เลือกอยู่ ไม่งั้นพอเลือกไปแล้วตัวเลือกอื่น
จะหายหมดจนเปลี่ยนกลับไม่ได้ ทดสอบยืนยันแล้วว่าเลือกกิจกรรมเดียวแล้วตัวเลือกยังครบสามรายการ

**เลือกปี** เป็น พ.ศ. 2565 ถึง 2700 เก็บเป็น ค.ศ. ในค่า แล้วบวก 543 ตอนแสดง
เปลี่ยนปีแล้วกิจกรรมที่เลือกไว้จะรีเซ็ตกลับเป็น "ทุกกิจกรรม"
เพราะกิจกรรมนั้นอาจไม่มีผลประเมินในปีใหม่

## กราฟคะแนนเฉลี่ย

เปลี่ยนจากกราฟเส้นเป็น **กราฟแท่ง** ไม่มีจุด
แกนเดือนแสดงเป็น `ม.ค. ก.พ. มี.ค.` ไม่มีเลขวันที่นำหน้า เพราะเป็นข้อมูลรายเดือน

**เดือนหนึ่งมีกี่กิจกรรมก็มีกี่แท่ง** แยกสีตามกิจกรรม พร้อมคำอธิบายสีใต้กราฟ
ชี้ที่แท่งแล้วเห็นชื่อกิจกรรม คะแนนเฉลี่ย และจำนวนผู้ตอบ

ที่ต้องแยกแท่งเพราะค่าเฉลี่ยรวมของทั้งเดือนบอกไม่ได้ว่างานไหนได้คะแนนน้อย
เดือนที่มีงานดีมากกับงานแย่มากปนกัน จะเห็นเป็นคะแนนกลาง ๆ ซึ่งซ่อนปัญหาไว้

สีผูกตามลำดับที่กิจกรรมปรากฏในรายการ ไม่สุ่ม กิจกรรมเดิมจึงได้สีเดิมทุกครั้งที่เปิดหน้า
ถ้าสุ่มสี ผู้ใช้จะจำไม่ได้ว่าแท่งสีไหนคืองานอะไร

ความกว้างของช่องเดือนโตตามจำนวนแท่งที่มากที่สุดในเดือนใดเดือนหนึ่ง
ทุกเดือนใช้ความกว้างเท่ากัน แท่งจึงขนาดเท่ากันหมดและเทียบด้วยตาได้ตรง ๆ

## การ์ดคะแนนเฉลี่ยรายข้อ เลื่อนดูทีละกิจกรรม

แสดงชื่อกิจกรรม จำนวนผู้ตอบ และคะแนนเฉลี่ยของกิจกรรมนั้น
พร้อมปุ่มลูกศรซ้ายขวาและตัวนับ `1/3` สำหรับเลื่อนไปดูกิจกรรมอื่น

เลือกกิจกรรมเดียวจากช่องด้านบนแล้วจะเหลือกิจกรรมเดียว ปุ่มลูกศรหายไปเอง
และตัวนับหน้าจะรีเซ็ตกลับเป็นกิจกรรมแรกทุกครั้งที่เปลี่ยนตัวกรอง

เพดานตรึงที่ 5 เสมอ ไม่ปรับตามข้อมูล ถ้าปรับตามข้อมูล เดือนที่ได้ 3.2
จะเห็นแท่งเต็มกรอบ ซึ่งอ่านแล้วเข้าใจผิดว่าดีเยี่ยม

ชี้ที่แท่งแล้วเห็นคะแนนกับจำนวนผู้ตอบของเดือนนั้น
เดือนที่ไม่มีใครตอบเว้นว่างไว้ ไม่วาดแท่งศูนย์

แถบคะแนนใช้เกณฑ์สีเดียวกันทั้งหน้า — เขียวตั้งแต่ 4 ทองตั้งแต่ 3 แดงต่ำกว่านั้น
และเทียบกับเต็ม 5 เสมอ ไม่ปรับเพดานตามข้อมูล ไม่งั้นคะแนน 3.2 จะดูเหมือนเต็ม

## ไม่ระบุตัวตน

**เซิร์ฟเวอร์ไม่ได้ดึง `user_id` ออกมาในทุกคิวรีของหน้านี้** ไม่ใช่แค่ไม่แสดงที่หน้าจอ
ยืนยันแล้วว่าข้อเสนอแนะที่ส่งกลับมามีแค่สามคีย์คือ `comment`, `created_at`, `event_title`

หน้าจอไม่ได้เขียนบอกเรื่องนี้ไว้ (ตามที่ขอ) การกันตัวตนจึงอยู่ที่โค้ดอย่างเดียว
ถ้าภายหลังมีคนแก้คิวรีให้ดึงชื่อผู้ตอบออกมา จะไม่มีข้อความบนหน้าจอคอยขัดแย้งให้สังเกตเห็น
ผู้ที่ดูแลโค้ดต่อควรรู้ไว้

ตาราง `event_feedback` ยังเก็บ `user_id` ไว้ เพราะจำเป็นสำหรับกันตอบซ้ำ
และรู้ว่าใครยังไม่ได้ตอบ แต่ไม่มี API ไหนส่งการจับคู่ "คนนี้ให้คะแนนเท่านี้" ออกไป

## หัวแบบประเมิน

```
[ป้าย] แบบประเมินความพึงพอใจ
(ชื่อกิจกรรม)
กรุณาประเมินความพึงพอใจต่อกิจกรรมที่ท่านเข้าร่วม
เพื่อนำความคิดเห็นไปพัฒนาการจัดกิจกรรมในอนาคต
```

ป้ายด้านบนบอกอยู่แล้วว่าเป็นแบบประเมิน บรรทัดหัวเรื่องจึงเหลือแค่ชื่อกิจกรรม
ไม่พูดซ้ำสองรอบในกรอบเดียวกัน

## วงกลมตัวเลือก วาดเองไม่ใช้ของเบราว์เซอร์

`accent-color` ย้อมได้แค่สีพื้นของปุ่มตัวเลือก ส่วนจุดตรงกลางเบราว์เซอร์วาดเอง
บางตัวจึงออกมาเป็น **จุดดำคาอยู่กลางวงแหวนสีเขียว** ดูเหมือนรูปรั่ว

แก้โดยซ่อน `<input type="radio">` ด้วย `sr-only` แล้ววาดวงกลมด้วย `<span>`
ซึ่งคุมสีได้ทั้งวง — ขอบกับจุดตรงกลางเป็นสีหลักเหมือนกัน

ยังคงเป็น `<input>` จริงที่ซ่อนไว้ ไม่ใช่ `<div>` ที่ทำท่าเป็นปุ่มตัวเลือก
คีย์บอร์ดกับโปรแกรมอ่านหน้าจอจึงใช้ได้เหมือนเดิม และวงแหวนตอนโฟกัส
ยังขึ้นผ่าน `peer-focus-visible`

# แก้บั๊ก: คะแนนหมดอายุขึ้นเป็นขีดกลาง

## สาเหตุ

การ์ดคะแนนอ่านจากคอลัมน์ `users.points_expire_at` ตรง ๆ
ซึ่งเป็นค่าว่างสำหรับพนักงานเกือบทุกคน เพราะคอลัมน์นี้มีไว้สำหรับกรณีพิเศษ
ที่ต้องกำหนดวันหมดอายุเองรายคนเท่านั้น

ส่วนวันตัดยอดจริงของทั้งระบบอยู่ในค่าตั้งระบบ (`points_expire_month`,
`points_expire_day` ค่าเริ่มต้น 31 ธันวาคม) ซึ่งการ์ดไม่เคยอ่าน

ผลคือพนักงานเห็นขีดกลาง แล้วเข้าใจว่าคะแนนอยู่ได้ตลอดไป
ทั้งที่ระบบตัดยอดทุกสิ้นปีอยู่แล้ว จะไปตกใจเอาตอนถูกตัดจริง

## ทางแก้

เพิ่ม `NextResetDate()` ที่คืนวันตัดยอดครั้งถัดไป

- ปีนี้ยังไม่ถึงวันตัดยอด → วันนั้นของปีนี้
- เลยมาแล้ว → วันเดียวกันของปีหน้า

เติมให้ตอนส่งข้อมูลผู้ใช้ออกไป **เฉพาะเมื่อยังไม่ได้ตั้งไว้รายคน**
ค่าที่กำหนดเองรายคนยังมีผลเหนือกว่าเสมอ

## ผลทดสอบ

```
ตั้ง 31 ธ.ค. (ค่าเริ่มต้น)        แสดง 2026-12-31
ตั้ง 30 มิ.ย. (เลยมาแล้วปีนี้)     แสดง 2027-06-30   ข้ามไปปีหน้า
ตั้งวันที่ 31 ในเดือนมิถุนายน      แสดง 2027-06-30   ถอยมาวันสุดท้ายของเดือน
ตั้งรายคนไว้ 2027-03-15           แสดง 2027-03-15   ไม่ถูกทับ
```

วันที่เปลี่ยนตามค่าตั้งระบบเอง เปลี่ยนวันตัดยอดในหน้าตั้งค่าแล้วพนักงานเห็นทันที
ไม่ต้องไปไล่แก้ทีละคน

# แก้บั๊ก: ปรับระดับสมาชิกแล้วเด้งกลับเป็นระดับเดิม

## สาเหตุ

ระบบคำนวณระดับจากคะแนนตลอดเวลา (`SyncTier` ทำงานทุกครั้งที่ล็อกอินและเปิดหน้าแรก)
การตั้งค่าระดับด้วยมือที่ขัดกับคะแนนจึงอยู่ได้แค่ชั่วคราว

ทำซ้ำได้ตามนี้

```
เริ่มต้น                   Elite / 5,200 คะแนน
ผู้ดูแลปรับเป็น Member      Member / 5,200   บันทึกสำเร็จ
พนักงานเปิดแอป             Elite / 5,200    เด้งกลับ
```

ผู้ดูแลจึงเห็นว่า "กดแล้วไม่เปลี่ยน" ทั้งที่ระบบบันทึกให้จริง

## ทางแก้ — เลิกให้แก้ระดับด้วยมือ

ช่อง **ระดับสมาชิก** ในฟอร์มแก้ไขพนักงานเปลี่ยนเป็นข้อความอ่านอย่างเดียว
พร้อมคำอธิบายว่าระบบคำนวณจากคะแนน และถ้าต้องการเลื่อนระดับให้ไปปรับคะแนนแทน

เซิร์ฟเวอร์ก็ไม่รับค่าระดับจากเส้นทางแก้ไขพนักงานแล้ว
เรียก API ตรงพร้อมส่ง `tier` มาก็ไม่มีผล

**ทางที่ถูกต้องคือปรับคะแนน** ซึ่งเปลี่ยนระดับให้เองทั้งขึ้นและลง และอยู่ถาวร

```
ลดคะแนนเหลือ 200    ->  Member / 200
เพิ่มคะแนนกลับ        ->  Elite / 5,200
เปิดแอปอีกครั้ง       ->  Elite / 5,200    ไม่เด้ง
```

## ทำไมถึงเลือกวิธีนี้ แทนการล็อกระดับไว้

อีกทางคือเพิ่มธง "ล็อกระดับ" ให้ระบบข้ามการคำนวณสำหรับคนนั้น
แต่จะได้สถานะที่อธิบายยาก เช่นพนักงานที่เป็น Elite ทั้งที่มี 0 คะแนน
และต้องตอบคำถามว่าทำไมคนนี้ไม่ถูกตัดระดับตอนสิ้นปี

ให้คะแนนเป็นที่มาของระดับเพียงทางเดียว เข้าใจง่ายกว่าและไม่มีข้อยกเว้นให้จำ
ถ้าภายหลังจำเป็นต้องล็อกระดับจริง ๆ บอกได้ครับ เพิ่มได้

## เรื่องการแจ้งเตือนพนักงาน

ระบบแจ้งเตือนเมื่อ **เลื่อนระดับขึ้น** อยู่แล้ว (`notifyTierUp`)
ส่วนการลดระดับจะเกิดจากการตัดยอดประจำปีเป็นหลัก ซึ่งบันทึกรายการไว้ว่า
*ตัดยอดคะแนนประจำปี และปรับระดับเป็น X* พนักงานย้อนดูได้ในประวัติคะแนน

# ตัดยอดคะแนนประจำปีทำงานอัตโนมัติอยู่แล้ว

ไม่ต้องมากดเอง ระบบตรวจ **ทุกชั่วโมง** ว่าถึงวันที่ตั้งไว้ในตั้งค่าระบบหรือยัง
และตรวจอีกครั้งทุกครั้งที่เปิดเซิร์ฟเวอร์ เผื่อเซิร์ฟเวอร์ปิดอยู่ตอนถึงกำหนด

ใช้ตัวตั้งเวลาในโปรแกรมแทน cron ของระบบปฏิบัติการ เพราะย้ายเครื่องแล้วตามไปด้วย
ไม่ต้องตั้งค่าเพิ่มที่เครื่องใหม่ และเปิดเซิร์ฟเวอร์หลายตัวก็ไม่ตัดยอดซ้ำ
เพราะเช็กก่อนทุกครั้งว่าปีนี้ทำไปแล้วหรือยัง

## ผลทดสอบ

ตั้งวันตัดยอดเป็นเมื่อวาน ล้างประวัติว่าเคยตัดแล้ว จากนั้นเปิดเซิร์ฟเวอร์เฉย ๆ
โดยไม่กดอะไรเลย

```
ก่อนเปิดเซิร์ฟเวอร์   คะแนนรวม 30,910 จาก 23 คน
เปิดเซิร์ฟเวอร์       ตัดยอดคะแนนประจำปี 2026 เรียบร้อย — 23 บัญชี คงระดับ 21 ลดระดับ 2
หลังเปิดเซิร์ฟเวอร์   คะแนนรวม 0 จาก 23 คน
```

## ปุ่มตัดยอดด้วยมือ

ปุ่ม **ตัดยอดคะแนนประจำปี** ในหน้าจัดการคะแนนยังอยู่ เผื่อต้องการตัดก่อนกำหนด
แต่ไม่ใช่ขั้นตอนปกติ

**เห็นปุ่มและกดได้เฉพาะคนที่ปรับคะแนนได้** คือผู้ดูแลระบบ หรือพนักงานที่อยู่ใน
แผนกหลังบ้านและมีตำแหน่งตั้งแต่ Chief Officer ขึ้นไป

ใช้สิทธิ์ชุดเดียวกับการปรับคะแนน เพราะการตัดยอดกระทบคะแนนและระดับของทุกคน
ในระบบพร้อมกันและย้อนกลับไม่ได้ จึงไม่ควรเปิดกว้างกว่าการปรับคะแนนของคนเดียว

กันที่เซิร์ฟเวอร์ด้วย ไม่ได้ซ่อนแค่ปุ่ม ทดสอบแล้ว

```
ผู้ดูแลระบบ                       ตัดยอดได้
GAG / Chief Officer               ตัดยอดได้
HRM / Manager                     ตัดยอดได้
HRD / Officer                     403 ไม่มีสิทธิ์ตัดยอดคะแนนประจำปี
PDF / Manager (นอกแผนกหลังบ้าน)   403 ไม่มีสิทธิ์เข้าหน้าผู้ดูแลระบบ
```

# รหัสพนักงานตั้งได้ตอนเพิ่มเท่านั้น

ช่องรหัสพนักงานถูกล็อกไว้ตอนแก้ไข ทั้งที่หน้าจอและฝั่งเซิร์ฟเวอร์

พร้อมจัดการชื่อผู้ใช้ให้ตามไปด้วย

# แก้สองอย่างในหน้าภาพรวม

## แถบตัวกรองใช้ช่องเลือกแบบเดียวกับหน้าอื่น

ทั้งหกช่อง (ช่วงวันที่ · ปี · เดือนถึงเดือน · แผนก · ระดับสมาชิก)
เปลี่ยนจาก `<select>` ของเบราว์เซอร์มาใช้ `Select` ของระบบ

`<select>` จัดสไตล์รายการตัวเลือกไม่ได้ เพราะเบราว์เซอร์วาดเอง
หน้าตาจึงหลุดจากส่วนอื่นและต่างกันไปในแต่ละเครื่อง

`Select` รับค่าที่เลือกมาตรง ๆ ไม่ใช่ event จึงต้องมีตัวช่วยแยกจาก `set` เดิม
และตัวเลือกเดือนเก็บค่าเป็นข้อความเพราะ `Select` เทียบค่าแบบตรงตัว

## เลือกเดือนเดียวแล้วกราฟบวมเต็มการ์ด

SVG ใช้ `viewBox` คู่กับ `minWidth: 100%` ถ้า viewBox แคบกว่ากรอบที่วาดจริงมาก
เนื้อหาทั้งหมดจะถูกขยายตามสัดส่วน

```
ก่อนแก้    1 เดือน -> viewBox กว้าง  76 · ขยาย 7.89 เท่า
หลังแก้    1 เดือน -> viewBox กว้าง 520 · ขยาย 1.15 เท่า
          12 เดือน -> viewBox กว้าง 912 · ขยาย 0.66 เท่า
```

แก้โดยตรึงความกว้างขั้นต่ำของพื้นกราฟไว้ที่ 520 แล้วจัดเนื้อหาไว้กลาง
ช่วงสั้นจึงวาดด้วยขนาดปกติและไม่ไปกองชิดซ้าย

ใช้กับกราฟทั้งสามตัวในระบบ และแถบรับเมาส์ขยับตามด้วย
ไม่งั้นชี้แล้วจะติดคนละเดือนกับที่เห็น

# สูตรของสามตัววัดในหน้าภาพรวม

ทั้งสามการ์ดมีไอคอน ⓘ ข้างหัวข้อ ชี้ค้างแล้วเห็นสูตร

| การ์ด | สูตร |
| --- | --- |
| แนวโน้มอัตราการเข้าร่วมกิจกรรม | `(จำนวนผู้เข้าร่วมเฉลี่ยต่อกิจกรรมในเดือนนั้น / จำนวนพนักงานทั้งหมด) × 100` |
| กิจกรรมที่ได้รับความสนใจสูงสุด | `(จำนวนผู้ลงทะเบียนในกิจกรรมนั้น / จำนวนพนักงานทั้งหมด) × 100` |
| อัตราการมีส่วนร่วมตามแผนก | `(จำนวนผู้เข้าร่วมเฉลี่ยต่อกิจกรรมของแผนก / จำนวนพนักงานทั้งหมดในแผนก) × 100` |

## อัตราการมีส่วนร่วมตามแผนก เปลี่ยนวิธีคิด

เดิมนับ "คนที่ไปอย่างน้อยหนึ่งงาน หารด้วยคนทั้งแผนก" ซึ่งเป็นการนับรายคน
ตอนนี้เปลี่ยนเป็น **เฉลี่ยต่อกิจกรรม** ตามสูตรข้างบน

เฉลี่ยหารด้วยจำนวนกิจกรรมทั้งหมดในช่วง ไม่ใช่เฉพาะกิจกรรมที่แผนกนั้นไป
ไม่งั้นแผนกที่ไปงานเดียวแต่ไปกันครบจะได้ 100% เท่ากับแผนกที่ไปครบทุกงาน
ซึ่งอ่านแล้วเข้าใจผิดว่ามีส่วนร่วมเท่ากัน

วิธีนี้ยังตรงกับกราฟแนวโน้มซึ่งมองที่ "เฉลี่ยต่อกิจกรรม" เหมือนกัน
ตัวเลขสองที่จึงเทียบกันได้

## คำกำกับใต้แถบใช้ตัวเลขดิบ ไม่ใช่ค่าเฉลี่ย

ค่าเฉลี่ยอย่าง 3 ÷ 8 = 0.375 ปัดกี่ตำแหน่งก็ไม่ลงตัว
ถ้าเขียนว่า "เฉลี่ย 0.4 คน" ผู้อ่านที่ลองคำนวณตามจะได้ 40%
ไม่ตรงกับ 37.5% ที่แสดงอยู่ข้าง ๆ แล้วคิดว่าระบบคำนวณผิด

จึงเขียนด้วยตัวเลขดิบแทน

```
ER    เข้าร่วมรวม 3 ครั้ง จาก 8 กิจกรรม · ทั้งแผนก 1 คน = 37.5%
ACC   เข้าร่วมรวม 2 ครั้ง จาก 8 กิจกรรม · ทั้งแผนก 1 คน = 25%
PDF   เข้าร่วมรวม 8 ครั้ง จาก 8 กิจกรรม · ทั้งแผนก 4 คน = 25%
```

ทดสอบแล้วคำนวณตามตัวเลขที่แสดงได้ตรงกับอัตราทุกแถว

# แก้บั๊ก: ตัวหารนับกิจกรรมที่ยังไม่เกิด

ตัววัดสองตัวที่คิดแบบ "เฉลี่ยต่อกิจกรรม" เคยหารด้วยกิจกรรมทั้งหมดในช่วง
รวมงานที่ยังไม่ถึงวันจัดด้วย

- อัตราการมีส่วนร่วมตามแผนก
- แนวโน้มอัตราการเข้าร่วมกิจกรรม

งานที่ยังไม่เกิดย่อมยังไม่มีใครเข้าร่วม ค่าเฉลี่ยจึงถูกถ่วงให้ต่ำลง
ตามจำนวนงานที่รออยู่ข้างหน้า

```
แผนกไป 1 งาน จากงานที่จบแล้ว 1 งาน
  หารด้วยงานที่จบแล้ว (1 งาน)   100%
  หารด้วยงานทั้งปี    (8 งาน)    12.5%
```

เลือกช่วง "ปีนี้" ตอนต้นปีแล้วทุกแผนกจะขึ้นเลขต่ำมาก ทั้งที่ยังไม่มีงานให้ไป

แก้โดยนับเฉพาะกิจกรรมที่จบไปแล้ว คิดจากวันสุดท้ายของงานบวกเวลาเลิก
ใช้เกณฑ์เดียวกับที่อื่นในระบบ

## ผลหลังแก้

```
ต.ค.  1 กิจกรรมที่จบแล้ว · เฉลี่ยมา 18 คน  = 75%
พ.ย.  3 กิจกรรมที่จบแล้ว · เฉลี่ยมา 6.7 คน = 27.8%

ER    2 ครั้ง จาก 4 กิจกรรมที่จบแล้ว · ทั้งแผนก 1 คน = 50%
```

ไม่ได้แก้ **กิจกรรมที่ได้รับความสนใจสูงสุด** เพราะตัวนั้นจัดอันดับกิจกรรมทีละงาน
ไม่ได้เฉลี่ยข้ามงาน งานที่ยังไม่จัดจึงแสดงยอดลงทะเบียนปัจจุบันได้ตามปกติ

## ชุดข้อมูลทดสอบ

เดิมกิจกรรมเกือบทั้งหมดอยู่ในอนาคต พอนับเฉพาะงานที่จบแล้วจึงเหลืองานเดียว
ที่ไม่มีคนลงทะเบียน หน้าภาพรวมขึ้น 0% ทั้งหน้า

เลื่อนสามงานที่มีคนลงทะเบียนให้จบไปแล้ว วันที่ตรงกับวันที่ลงทะเบียน
เรื่องราวจึงสมเหตุสมผลและเห็นตัวเลขจริงบนทุกการ์ด

## สองข้อจำกัดที่ยังอยู่ (ไม่ใช่บั๊ก แต่ควรรู้ตอนอ่าน)

**แผนกเล็กค่ากระโดดเป็นขั้น** แผนก 1 คนกับ 4 งานที่จบแล้ว
ค่าที่เป็นไปได้มีแค่ 0 · 25 · 50 · 75 · 100% ไม่มีค่าระหว่างนั้น
การเรียงอันดับระหว่างแผนกที่มีคนเดียวจึงแทบไม่มีความหมาย

**งานที่ไม่ได้เชิญทุกแผนก** เช่นอบรมเฉพาะฝ่ายผลิต ยังถูกนับเป็นตัวหาร
ของแผนกอื่นด้วย แผนกที่ไม่ได้ถูกเชิญจึงดูมีส่วนร่วมต่ำ
จะแก้ให้ตรงต้องเก็บว่าแต่ละงานเชิญแผนกไหนบ้าง ซึ่งระบบยังไม่มีข้อมูลส่วนนั้น

# แก้บั๊ก: กิจกรรมร่างถูกนำมาคิดในรายงาน

## สิ่งที่ควรเป็น

| สถานะกิจกรรม | นับในรายงานไหม | เหตุผล |
| --- | :---: | --- |
| เปิดรับ | ✓ | กำลังใช้งานอยู่ |
| ปิดแล้ว | ✓ | เคยเปิดรับและเกิดขึ้นจริง แค่ปิดรับลงทะเบียนแล้ว |
| **ร่าง** | ✗ | ยังไม่เผยแพร่ พนักงานมองไม่เห็นและลงทะเบียนไม่ได้ |

## สิ่งที่เป็นจริงก่อนแก้

คิวรีของรายงานไม่ได้กรองสถานะกิจกรรมเลย **กิจกรรมร่างจึงถูกนับเป็นตัวหารด้วย**

ทดสอบโดยสร้างกิจกรรมร่างแล้วดูตัวเลขขยับ

```
ก่อนเพิ่มกิจกรรมร่าง                 นับ 4 งาน · แผนกแรก 2/4 = 50%
หลังเพิ่มกิจกรรมร่าง (ยังไม่มีคนลง)   นับ 5 งาน · แผนกแรก 2/5 = 40%
หลังมีคนลงทะเบียนในกิจกรรมร่าง        นับ 5 งาน · แผนกแรก 3/5 = 60%
```

ผู้ดูแลที่เตรียมงานไว้ล่วงหน้าแล้วกดบันทึกร่าง จะเห็นอัตราการมีส่วนร่วม
ตกลงทันทีทั้งที่ยังไม่มีอะไรเกิดขึ้น

## หลังแก้

เพิ่มเงื่อนไข `e.status <> 'draft'` ให้ทุกคิวรีในหน้าภาพรวม ได้แก่
สถิติด้านบน · แนวโน้มอัตราการเข้าร่วม · กิจกรรมที่ได้รับความสนใจสูงสุด ·
อัตราการมีส่วนร่วมตามแผนก · ความถี่การเข้าร่วมของพนักงาน

```
ก่อนเพิ่มกิจกรรมร่าง                 นับ 4 งาน · 50%
หลังเพิ่มกิจกรรมร่าง                 นับ 4 งาน · 50%   ไม่ขยับ
หลังมีคนลงทะเบียนในกิจกรรมร่าง        นับ 4 งาน · 50%   ไม่ขยับ
```

ทดสอบสลับสถานะของกิจกรรมจริงที่มีคนลงทะเบียนแล้วด้วย

```
Sport Day สถานะ 'เปิดรับ'   นับ 4 งาน · 50%
Sport Day สถานะ 'ปิดแล้ว'   นับ 4 งาน · 50%     ยังถูกนับ
Sport Day สถานะ 'ร่าง'      นับ 3 งาน · 33.3%   หายไปจากรายงาน
```

# กติกาการนับกิจกรรมในรายงาน

| สถานะ | นับไหม | นับเมื่อไหร่ |
| --- | :---: | --- |
| ร่าง | ✗ | — |
| เปิดรับ | ✓ | ทันทีที่เผยแพร่ ไม่ต้องรอให้งานจบ |
| ปิดแล้ว | ✓ | นับต่อไปเหมือนเดิม |

**กิจกรรมที่ยังไม่มีใครลงทะเบียนนับเป็น 0 ในค่าเฉลี่ย ไม่ใช่ข้ามไป**
เพราะงานที่เปิดแล้วไม่มีคนสนใจก็เป็นข้อมูลที่ต้องเห็น

เดิมนับเฉพาะกิจกรรมที่จบแล้ว ตอนนี้เอาเงื่อนไขนั้นออก
ผู้ดูแลจึงเห็นยอดของงานที่กำลังเปิดรับได้ตั้งแต่ตอนนี้ ไม่ต้องรอจนงานจบ

## ผลทดสอบ

```
ต.ค.  1 งาน · เฉลี่ยมา 18 คน = 75%
พ.ย.  5 งาน · เฉลี่ยมา 5.4 คน = 22.5%
ธ.ค.  2 งาน · เฉลี่ยมา 0 คน  = 0%     งานยังไม่ถึงวัน นับเป็น 0

เพิ่มงานเปิดรับที่ยังไม่มีคนลงทะเบียน
  กิจกรรมในกราฟ  8 -> 9 งาน
  แผนกแรก        3/8 = 37.5%  ->  3/9 = 33.3%     ถูกนับเป็น 0 จริง

สลับสถานะ Sport Day
  เปิดรับ   8 งาน · 37.5%
  ปิดแล้ว   8 งาน · 37.5%     เท่ากัน
  ร่าง      7 งาน · 28.6%     หายไปจากรายงาน
```

# ลงทะเบียน กับ เข้าร่วมจริง ต่างกันไหม

**ตอนนี้ไม่ต่างกันเลย** ทุกการลงทะเบียนถูกบันทึกเป็น `attended` ทันที
ไม่ว่ากิจกรรมนั้นจะตั้งพิกัดไว้หรือไม่

```go
atVenue := venueLat.Valid && venueLng.Valid
status := "attended"      // ตั้งเป็น attended เสมอ ไม่ได้ดู atVenue
```

ตรวจในฐานข้อมูลจริง มี 45 รายการ เป็น `attended` ทั้งหมด
และทั้ง 45 รายการมาจากกิจกรรมที่ **ไม่ได้ตั้งพิกัด** สักงานเดียว

ผลที่ตามมา

- ช่อง **อัตราการเข้าร่วม** แสดง 100% เสมอ
- ช่อง **ไม่มาตามนัด** แสดง 0 เสมอ

ทั้งสองช่องจึงไม่ได้ให้ข้อมูลอะไร

## ถ้าต้องการให้สองค่านี้ต่างกันจริง

ต้องแยกสองขั้นตอนออกจากกัน ข้อเสนอคือ

| สถานะ | เมื่อไหร่ |
| --- | --- |
| `attended` | กิจกรรมที่ตั้งพิกัด ระบบตรวจตำแหน่งตอนกดลงทะเบียน จึงยืนยันว่ามาถึงงานจริง |
| `registered` | ยังไม่ยืนยันว่ามาถึง ผู้ดูแลกดเช็คอินหน้างานให้ภายหลังได้ |

**คะแนนไม่เปลี่ยน** พนักงานยังได้ทันทีที่ลงทะเบียนเหมือนเดิม
และเช็คอินจะไม่จ่ายคะแนนซ้ำ มีแต่คนที่มาหน้างานโดยไม่เคยลงทะเบียนที่ได้คะแนนตอนเช็คอิน

เคยทำไว้แล้วรอบหนึ่งและถูกย้อนออกไป ถ้าต้องการให้ใส่กลับ บอกได้ครับ

# แก้บั๊ก: ป็อปอัปฝั่งพนักงานเด้งทับหน้าผู้ดูแลระบบ

## อาการ

บัญชีที่เข้าได้ทั้งสองฝั่ง (พนักงานแผนกหลังบ้าน) ถ้าล็อกอินฝั่งพนักงานก่อน
แล้วเปลี่ยนไปเลือกช่องผู้ดูแลระบบด้วยรหัสเดิม จะเจอป็อปอัปประกาศข่าวสาร
และป็อปอัปฉลองเลื่อนระดับสมาชิกขึ้นมาทับหน้าผู้ดูแลระบบ

## สาเหตุ

ป็อปอัปทั้งสามตัวเช็กแค่ `role` ของผู้ใช้

```js
user?.role === 'user' && !!user?.terms_accepted_at
```

พนักงานแผนกหลังบ้านมี `role` เป็น `user` อยู่แล้ว (สิทธิ์เข้าหลังบ้านมาจาก
แผนกกับตำแหน่ง ไม่ใช่จาก role) เงื่อนไขนี้จึงเป็นจริงทั้งสองฝั่ง

ที่ลำดับการล็อกอินมีผล เพราะ `terms_accepted_at` ถูกตั้งตอนกดยอมรับ PDPA
ในฝั่งพนักงาน ถ้าเข้าฝั่งผู้ดูแลระบบอย่างเดียวตั้งแต่แรก ค่านี้ยังว่าง
ป็อปอัปจึงไม่เด้ง พอเข้าฝั่งพนักงานก่อนแล้วกลับมา ค่านี้มีแล้วจึงเด้ง

## ทางแก้

เพิ่ม `useEmployeeArea()` ที่ดูจากเส้นทางปัจจุบันว่าอยู่หน้าไหน
แล้วใช้เป็นเงื่อนไขร่วมของทั้งสามตัว

| ป็อปอัป | ไฟล์ |
| --- | --- |
| ประกาศข่าวสาร | `components/AnnouncementGate.jsx` |
| แบบประเมินความพึงพอใจ | `components/FeedbackGate.jsx` |
| ฉลองเลื่อนระดับสมาชิก | `components/TierLevelUp.jsx` |

ดูจากเส้นทางแทนที่จะดูจากช่องที่เลือกตอนล็อกอิน เพราะผู้ใช้สลับไปมาระหว่าง
สองฝั่งได้โดยไม่ต้องล็อกอินใหม่ ถ้าจำจากตอนล็อกอินจะผิดทันทีที่สลับฝั่ง

## ผลทดสอบ

ไล่ทุกบทบาทกับทุกเส้นทาง

```
                        ฝั่งพนักงาน      หน้าผู้ดูแลระบบ
พนักงานทั่วไป            เด้งครบ 3 ตัว    ไม่เด้ง
พนักงานหลังบ้าน          เด้งครบ 3 ตัว    ไม่เด้ง
ผู้ดูแลระบบ              ไม่เด้ง          ไม่เด้ง
พนักงานยังไม่รับ PDPA     ไม่เด้ง          ไม่เด้ง
```

# ปิดช่องโหว่ที่เหลือของป็อปอัปเลื่อนระดับ

`TierLevelUp.jsx` เช็กว่าอยู่ฝั่งพนักงานก่อน **เริ่มดึงข้อมูล** แล้ว
แต่ยังไม่ได้เช็กซ้ำตอน **วาดป็อปอัป** จึงยังหลุดได้สองทาง

**หนึ่ง การดึงข้อมูลเป็นงานที่รอผลลัพธ์** ถ้าเริ่มดึงตอนอยู่ฝั่งพนักงาน
แล้วผู้ใช้กดเข้าหน้าผู้ดูแลระบบก่อนผลจะกลับมา ป็อปอัปจะถูกตั้งค่า
แล้วโผล่บนหน้าผู้ดูแลระบบ

**สอง ป็อปอัปที่เปิดค้างอยู่แล้ว** ถ้าผู้ใช้สลับฝั่งตอนที่ยังไม่กดปิด
ตัวที่เปิดไว้จะค้างอยู่ เพราะไม่มีใครสั่งให้หายไป

เพิ่ม `if (!inEmployeeArea) return null;` ที่ส่วนวาด ปิดได้ทั้งสองทาง

เลือก **ซ่อนเฉย ๆ ไม่ล้างค่าทิ้ง** พอกลับมาฝั่งพนักงานจะได้เห็นคำฉลองเหมือนเดิม
เพราะยังไม่ได้กดรับทราบ ถ้าล้างทิ้งพนักงานจะพลาดการฉลองไปเลย

## ผลทดสอบ

```
                              ก่อนแก้        หลังแก้
ดึงข้อมูลค้างแล้วสลับฝั่ง       วาดป็อปอัป     ไม่วาด
ป็อปอัปเปิดค้างแล้วสลับฝั่ง      วาดป็อปอัป     ไม่วาด
อยู่ฝั่งพนักงานตามปกติ          วาดป็อปอัป     วาดป็อปอัป
```

อีกสองตัว (ประกาศข่าวสาร และแบบประเมิน) เช็กซ้ำตอนวาดอยู่แล้วด้วย
`if (!active || !current) return null;` จึงไม่มีปัญหานี้
